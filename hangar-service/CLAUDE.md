## Service and auth

**Service — `hangar-service/` on Cloud Run, NOT in the cluster:** FastAPI + Firestore (Native, `us-central1`) in GCP project `revenant-discord-bot-2`, region `us-central1`, image in Artifact Registry `us-central1-docker.pkg.dev/revenant-discord-bot-2/revenant/hangar-service:<git-short-sha>` (never `:latest`), runtime SA `hangar-runtime@` (`roles/datastore.user`). **min-instances 1** (~$7/month): a cold Python/Firestore start plus the Wiki vehicle-index warm-up exceeds voice's 6s tool bound and Discord's 3s autocomplete deadline. Catalog data is cached 12h stale-while-revalidate, warmed at startup; Cloud Run runs request-only CPU, so a background refresh may finish on a later request (accepted). Deploy commands, env and API: `hangar-service/README.md`.

**Auth — the app is the only gate, and the audience must match byte for byte:**
- **Cloud Run invoker IAM check is OFF (`--no-invoker-iam-check`, since the web editor).** The org's domain-restricted-sharing policy (`iam.allowedPolicyMemberDomains`) blocks an `allUsers` invoker, so `--allow-unauthenticated` fails — and browsers coming through the load balancer can't present a Google invoker token at all. So this ONE service (the org policy is untouched) skips Cloud Run's invoker check and **the app's own authentication is the only gate**: Google ID tokens for the bot and sc-knowledge (unchanged — same `run.app` URL, same exact audience), Discord session cookies for browsers. Every `/v1` and `/api/v1` route stays authenticated; only `/health`, `/version.txt` and the static editor files are open, and none carries member data. The old `roles/run.invoker` binding for `hangar-api@` is still there (harmless; needed again if the check is ever re-enabled). Do NOT "fix" an open `/health` by re-enabling the check — it would lock every browser out. Unauthenticated surface (none of it returns member data): `/health`, `/healthz`, `/version.txt`, the static editor, and the login routes `/api/auth/login|callback|logout` plus `/api/me` (401 without a session). The two `run.app` URLs are exactly as public as `hangar.aklabs.io` — never rely on the load balancer for access control (the `__Host-` cookie isn't sent there and session writes require `HANGAR_PUBLIC_ORIGIN`, so this is safe today).
- **The app re-verifies** the Google-signed ID token (audience `HANGAR_AUDIENCE`, `email_verified`, email in `HANGAR_ALLOWED_CALLERS`) and enforces writes: `X-Acting-Member` must equal the path member or be in `HANGAR_ADMIN_IDS` (same ids as `BOT_ADMIN_USER_IDS`). Reads of any member are allowed (UC2b).
- Cloud Run serves two URLs — `https://hangar-service-hvmf2jpuca-uc.a.run.app` and `https://hangar-service-278098364045.us-central1.run.app`. **The audience is exactly `https://hangar-service-hvmf2jpuca-uc.a.run.app`** (no trailing slash); callers mint for, and call, that URL. Using the other form is a 401.
- **Health is `/health`, not `/healthz`:** Cloud Run's front end reserves paths ending in `z` (Google's own 404). `/healthz` stays for local parity. `/health` is open (invoker check off).

## Data model and catalog

**Data model:** Firestore `members/{discordId}/ships/{shipId}` = `{vehicleUuid, vehicleName, vehicleClassName, nickname, fitted: {<slot>: {itemUuid, itemName}}, createdAt, updatedAt, updatedBy}`. `fitted` holds ONLY changes from stock (fitting a slot's stock item clears it). A member may own several of one model; nicknames disambiguate. The **effective loadout** = stock slots with `fitted` applied, each `{slot, type, sizeMin, sizeMax, compatibleTypes, item, source: stock|fitted}`. Member ids must be numeric (1–32 digits).

**Catalog — from Star Citizen Wiki vehicle `ports[]`:** a port is a slot when its OWN `editable` is true and its type (or, empty in stock, a compatible type) is QuantumDrive, Shield, PowerPlant, Cooler, Radar, WeaponGun, Turret, MissileLauncher, WeaponMining or TractorBeam. **Nesting rule:** ports are walked at every depth and the parent's `editable_children` is NOT used — live data has S5 turret gimbals with `editable_children: false` while the gun inside is `editable: true`, so following the flag would hide every swappable turret gun. Slot ids join port names with `/` at whatever depth the port sits (no cap; e.g. three levels deep on the Taurus's manned upper turret: `hardpoint_turret_base_upper/hardpoint_weapon_left/hardpoint_class_2`). **Refitting a parent slot hides its stock children.** **Missiles are not tracked** (fit check answers `not_tracked`); racks are `editable: false` on the ships checked.

## Web editor — server side

**Web editor — `https://hangar.aklabs.io` (project 2, since 2026-10-09).** Spec: `docs/superpowers/specs/2026-10-09-hangar-editor-design.md`. React SPA in `hangar-editor/` (README there) where members sign in with Discord and manage ships, fit slot by slot from only-compatible items (sorted by the same key stat `sc_compare_components` ranks by, with the cheapest UEX shop price), reset to stock, view other members' hangars, and import spviewer loadouts. Same Firestore data, so edits show up immediately in `/hangar list` and the bot's tools.
- **Architecture:** Cloud DNS zone `zone-hangar-aklabs-io` (delegated by NS records at the `aklabs.io` DNS provider) → static IP `hangar-editor-ip` → global external HTTPS LB (`EXTERNAL_MANAGED`, managed cert `hangar-editor-cert`, HTTP→HTTPS redirect) → serverless NEG `hangar-editor-neg` → the SAME Cloud Run `hangar-service`, which serves the API **and** the built SPA (one image, multi-stage Dockerfile, build context = repo root). URL map: every path → hangar-service. **Why no public GCS bucket for the SPA (unlike the owner's home-build app):** that app's project has no parent org; `revenant-discord-bot-2` sits under an org whose domain-restricted sharing blocks `allUsers` on buckets as well as Cloud Run, so a public bucket is impossible without loosening the org policy. Infra is scripted idempotently in `hangar-service/scripts/setup-domain.sh` (create-if-missing; pauses for the NS step only when it creates the zone; ends with `--no-invoker-iam-check`). Gotcha: a `url-maps import` YAML must NOT contain `kind:`.
- **Static serving:** hashed `/assets/*` immutable for a year; root files (favicon) 1h; any other GET outside `/api`, `/v1`, `/health`, `/healthz`, `/assets` → `index.html` `no-cache` (client routes survive reloads; a deploy is picked up on the next navigation) with a strict CSP (self-only script/style; `img-src` allows Discord CDN avatars plus the image hosts in `IMAGE_ORIGINS`, built from `catalog.IMAGE_HOSTS` (`cdn.star-citizen.wiki`, `media.starcitizen.tools`, `cstone.space`) and `data:`; `frame-ancestors 'none'`; `HANGAR_RUM_ORIGINS` adds Dynatrace RUM origins). The fallback hooks the router's 404, so API routing is unchanged. `/version.txt` = the image's git SHA.
- **Discord OAuth2** (authorization code, scope `identify guilds.members.read`, client ID `1558216042151419935`, redirect `https://hangar.aklabs.io/api/auth/callback`). **Login gate = Discord server membership:** the callback checks `GET /users/@me/guilds/{id}/member` for each id in `HANGAR_ALLOWED_GUILD_IDS` (production `323349603976216577`, the main server). Not a member → `/?login_error=not_member`, no cookie; empty/missing list → browser login disabled (503), never "allow everyone". Membership is checked only at login.
- **Sessions:** stateless signed (itsdangerous) `__Host-hangar_session` cookie, `HttpOnly; Secure; SameSite=Lax; Path=/`, 30 days; payload = public Discord profile fields + `guildId` + `iat`. Rotation: `HANGAR_SESSION_KEY_PREVIOUS` keeps old sessions valid; `HANGAR_SESSION_NOT_BEFORE=<unix s>` logs everyone out (the only revoke — there is no per-session store). A session principal's acting member is its own Discord id; `X-Acting-Member` is ignored for it; the write rule is unchanged (own hangar, or `HANGAR_ADMIN_IDS`).
- **CSRF:** session writes (and logout) require same-origin — `Origin` (else `Referer`) must equal `HANGAR_PUBLIC_ORIGIN`; plus `SameSite=Lax`. Service-token callers are unaffected.
- **spviewer import:** the member runs a console snippet on spviewer.eu that downloads their IndexedDB `SCSPVDatabase` → `vehiclesLoadout` rows; `POST /api/v1/import/spviewer/preview|apply` decode `loadoutData` (vendored LZ-string). **The real choices live in the `selected*` maps** (`selectedShields`, `selectedPilotWeapons`, …), each paired with its `*Ports` array by category; the `Loadout` field is only the fallback (the real export's `Loadout`s are all stock). Apply re-decodes server side (never trusts client changes) and is **authoritative**: the ship's whole `fitted` map is replaced, so slots the loadout doesn't change go back to stock — and therefore a row whose analysis is incomplete (a `too_many_lookups` skip, an unknown `selected*` category, any row-level skip) is **refused, never written**, or it would wipe existing fittings. Caps: 2 MB upload, 100 rows, 500 ports/row, 2 MB decoded per row (16 MB/request), **32 distinct Wiki item lookups per request** (the Wiki client's 60/min limiter is shared with the bot's hangar reads), at most 2 imports in flight per instance (`asyncio.Semaphore(2)`, 503 `busy`, body read before a slot is taken). Cloud Run memory 1 GiB for that.
- **Secrets:** `hangar-discord-client-secret` and `hangar-session-key` in Secret Manager only (`--set-secrets`, readable by `hangar-runtime@`); never in env files, git or images. **`.env_*` lesson:** the owner's local hangar env file is named `.env_sc_hanger` — the root `.gitignore`/`.dockerignore` cover `.env_*` explicitly, and `hangar-service/Dockerfile.dockerignore` is an allow-list (`*`, then only the service + editor sources; `**/.env*`, `**/*key*.json`, `OrgGuides` excluded) because the image build context is now the repo root.
- Deploy/env/build: `hangar-service/README.md`; editor dev/test: `hangar-editor/README.md` (Node ≥ 22.12; the bot's Jest ignores `hangar-editor/`, whose tests are Vitest).

## Ship wireframes — server side

Spec: `docs/superpowers/specs/2026-10-11-ship-wireframes-design.md`. The viewer is in `hangar-editor/CLAUDE.md`; the pipeline and bundle format are in `tools/wireframes/CLAUDE.md`; the HARD RULE on extracted game data is in the root `CLAUDE.md`.

- **Storage:** private GCS bucket from `HANGAR_MODELS_BUCKET` (production `revenant-discord-bot-2-hangar-models`, uniform access, no public access; `hangar-runtime@` needs `roles/storage.objectAdmin` on it) at `models/<kind>/<className>.swf.gz`; Firestore `models/{kind}:{className}` = `{kind, className, vehicleUuid|null, vehicleName|null, lines, bytes, sha256, build, slots: {matched, missing, ambiguous}, uploadedBy, uploadedAt}` (`models.py`; metadata written AFTER the object and the object is removed if that fails (a NEW model leaves nothing; a failed RE-upload leaves the previous model listed but possibly without bytes until re-uploaded; a failed cleanup logs a WARNING naming the orphan), delete removes metadata first then the object). **Bucket unset → ONLY the model routes answer 503 `unavailable`**, `hasWireframe` is simply false, everything else unaffected. The bucket is private (never public) because the org's domain-restricted-sharing policy blocks `allUsers` anyway and the data must not be public; the service streams bytes to authenticated members.
- **Upload validation (`swf.py`, 400 `invalid_request` naming the problem; over 2 MB → 413 `too_large`):** body ≤ 2 MB; gzip decompressing to ≤ 8 MB; magic `SWF1`; header JSON object with all required keys, `format == 1`, `space == "gltf-y-up-m"`, `kind == "vehicle"`, `className` matching `[A-Za-z0-9][A-Za-z0-9_.-]{0,127}`, `center` three numbers, `halfExtent` > 0, `lines` ≤ 80,000, `nodes` ≤ 5,000 well-formed entries whose parent links form a forest (a cycle would hang slot matching); payload length must equal `lines × 12`. The server never renders lines; it stores the bytes verbatim.
- **Canonical class name:** the header `className` is resolved with the catalog's `vehicle_by_class_name`; when it matches, the catalog's own casing is used as the storage key, so there is one model per vehicle. An unknown class is still stored (`vehicleUuid: null`), listable and deletable, but writes no positions.
- **Slot matching (`slot_match.py`):** for each catalog slot id `a/b/c`, take every node named `a` (case-insensitive), then for each further segment the nearest descendants with that name (BFS, not descending past a match). Exactly one → `{xyz}`; none → `missing`; several → the first if all lie within `COINCIDENT_M = 0.05` m of each other (duplicate nodes at one spot), otherwise `ambiguous` (no position). **Positions doc it writes:** `vehiclePositions/{vehicleUuid}` is REPLACED with `{slots, space: "gltf-y-up-m", source: "extracted", className, updatedAt, updatedBy}` on every upload (hand-placed 2D points are not preserved — none existed). **Delete** removes the positions doc ONLY when `source == "extracted"` AND its `className` equals the deleted model's, so it can never remove another source's data. A positions-store failure after the bundle was stored rolls the bundle back.
- **Routes (all `/api/v1`, browser API only):** admin = session principal in `HANGAR_ADMIN_IDS` (service tokens and non-admins get 403) — `POST /api/v1/models` (raw `application/octet-stream`, same-origin enforced), `GET /api/v1/models` (list, sorted by kind then class name), `DELETE /api/v1/models/{kind}/{className}` (204, 404 if absent; same-origin). Member: `GET /api/v1/models/vehicle/{uuid}/wireframe` (any authenticated principal) → bytes with `ETag: "<sha256>"`, `Cache-Control: private, max-age=86400`, 304 on `If-None-Match`, 404 when none; `Content-Encoding` is NOT set (the client gunzips with `DecompressionStream`). `/catalog/vehicles/{uuid}/slots` carries `vehicle.hasWireframe` (false when the store is unconfigured or errors, logged WARNING). Logs: INFO `hangar: model upload kind=… class=… vehicle=… lines=… bytes=… matched=… missing=… ambiguous=… by=…` and `hangar: model delete … positions_removed=…`.
- **Known limits:** a ship whose model lacks catalog hardpoints gets no marker for them (the 890 Jump's 7 Wiki PDC ports are absent from the model: 19/26 matched); duplicate nodes at different positions are `ambiguous` and get no marker (Ironclad Assault 31/33 — duplicate `hardpoint_quantum_drive`/`hardpoint_radar`); `kind: "item"` is not accepted by the server yet; the model is the parked pose (landing gear down); the pipeline cannot read Draco/meshopt or external buffers. The missing/ambiguous figures are spec spike measurements, not asserted by tests.

## RSI hangar import (HTF) and pledge leaderboard

**RSI hangar import — Hangar Transfer Format / HangarXPLOR (since 2026-10-11).** Spec: `docs/superpowers/specs/2026-10-11-hangar-htf-import-design.md`. Members import their RSI pledge hangar into the editor and re-import later to stay in sync; imported ships carry their pledge data, which feeds a public pledge leaderboard (friendly ribbing). **Format:** HTF is a DRAFT community spec (OpenAPI `https://docs.starcitizen.fans/hangar-transfer-format.yaml`, v0.0.1) — a JSON array of entities; the producer in practice is HangarXPLOR's "Download JSON" → `shiplist.json` (one element per ship; a package pledge yields several with the same `pledge_id`; `ship_name` is the member's custom RSI name if set; `pledge_date` is RSI date text; `pledge_cost` like `"$350.00 USD"`; a selection export is possible, so a file may be partial; no components). Pure logic is `hangar-service/src/htf.py`, routes are in `app.py` (`/import/htf/preview|apply`, `/pledges/leaderboard`). **Matching** per ship entity (`entity_type` other than `ship` → skipped `not_a_ship`): first `ship_code` == a catalog vehicle `className` (case-insensitive), else `name` through the existing vehicle resolver (`resolve_vehicle`); `ship_name` (the member's CUSTOM RSI name) is used ONLY when `name` is empty/absent, never as a fallback from an unmatched `name` (a concept Kraken named "Arrow" must not become an Arrow); ambiguous/none → skipped `unmatched`. Live coverage 2026-10-11: 144 of 186 HTF ship codes match a Wiki `className`; most misses are concept ships absent from the in-game catalog (Kraken, Odyssey, Nautilus, Pioneer, Merchantman…) — they cannot become hangar ships. **Sync key:** `rsi.key = "<pledge_id>:<ship_code lowercased>:<ordinal>"`, ordinal = 0-based index among same-code ships of the same pledge in file order (a pledge with two Pisces → two ships). **Row kinds:** `new`; `existing` (a ship already has that key → pledge fields refresh, nickname only changes when RSI's custom name changed since the last import, so a manual rename survives); `link` (no key match but the member has hand-added, non-RSI ships of the same vehicle not already claimed by an earlier row → `linkCandidates`, first is the default, client may choose `"new"`); `skipped` (unmatched rows carry `countedInTotals: true` — they still count in the pledge total). `missing` = RSI-sourced ships whose key is absent from the file, with `defaultRemove = no fittings`; **`partial`** = fewer than 50% of the member's RSI ships (and the member has ≥2) appear in the file → every `defaultRemove` forced false and the editor shows "This export looks like a selection — nothing will be removed by default". Preview writes nothing. **Apply re-derives everything server side** (never trusts client rows): `choices {links, remove}` are validated against the re-derived result — a link for a non-`link` row, a target not in that row's `linkCandidates`, two rows targeting one ship, or a `remove` of a ship not in `missing` → **400 `invalid_request` naming it, nothing written**; an empty vehicle index (or an unreadable catalog) → **503** rather than classifying every row as unmatched and every RSI ship as missing. Writes go ship by ship with per-row results (`created|linked|updated|unchanged|skipped|error`) plus `removed` and `ledgerSynced`; fittings are never touched except by deleting a removed ship; re-applying the same file is all `unchanged`. Logs one INFO line per apply: `hangar: htf import member=<id> created=… linked=… updated=… removed=… skipped=…`. **Ship `rsi` map** (absent on hand-added ships): `{key, pledgeId, shipCode, ordinal, pledgeName, pledgeDate, pledgeDateIso, pledgeCost {amount, currency, raw}, lti, warbond, rsiName, importedAt}`; `pledgeCost` parses `$`/`€`/`£` or a 3-letter code, unparseable → amount/currency null, raw kept. **Pledge LEDGER `members/{id}/rsiPledges/{pledgeId}`** `{pledgeId, name, date, dateIso, cost, lti, warbond, ships[{shipCode,name,rsiName,vehicleUuid,matched}], importedAt}` is written on every apply for EVERY ship-bearing pledge in the file, matched or not — **why:** concept-ship pledges can't become hangar ships but must still count toward the total, so totals and the leaderboard come from the ledger, never from ships. Each apply upserts the file's pledges and deletes ledger pledges absent from it only when the import is neither `partial` nor `ledgerPartial` (file's pledge ids cover < 50% of the member's ≥2 existing ledger pledges; exposed in the preview, editor banner shows for either) and never a pledge backing a `missing` ship the user kept; a ledger failure after the ships were written is logged and reported as `ledgerSynced: false`. **Totals rule:** a pledge counts ONCE per distinct `pledgeId` (first parsed amount, so a package of three ships isn't tripled), **per currency** (no FX; USD ranked first), and is always labelled "pledged on ships" — HangarXPLOR exports only ship-bearing pledges, so paints, game packages, gear and melted items are excluded, and CCU'd pledges count at current value. **Privacy decision (owner's deliberate choice):** full pledge data INCLUDING cost is stored and visible to every signed-in guild member and to the bot (the group are IRL friends; the leaderboard is for good-natured ribbing) — don't add per-member hiding without asking. **Surfaces:** `GET /v1/pledges/leaderboard` (service tokens + sessions, also under `/api/v1`) → `{entries: [{member, displayName|null, totals, pledges, ships, lti, topPledge, lastImport}], caveat}` sorted by USD total desc, then other-currency sum, then member id; only members with ≥1 RSI-sourced ship; computed per request, no cache. `GET /v1/members/{id}/hangar` adds `pledgeSummary {totals, pledges, ships, lti}` when the member has RSI ships and the ledger has pledges — **omitted (logged WARNING) if the ledger read fails**, so a ledger outage never fails a hangar read. **`/hangar leaderboard`** (bot, **public**, non-ephemeral, `allowedMentions` none): 🥇🥈🥉 then `4.`…, name resolution registry `addressName` → `SpeakerNames` override → the service's `displayName` → `<@id>` (markdown-escaped), per line totals · ships · LTI ship count (`lti` = ships in LTI pledges) · top pledge (labelled by its END-STATE ships via `htf.pledge_label` — RSI never renames a pledge after a CCU, so an Aquila pledge upgraded to an Ironclad Assault still has `pledge_name` "Standalone Ships - Constellation Aquila"; packages read "Starfarer + Cutlass Black" / "2× Pisces C8", max three names; the RSI title stays available as `topPledge.pledgeName`; markdown-escaped, clamped to 60 chars), the service caveat plus `last import <oldest lastImport date>` as an italic footer, ≤2000 chars (`…and N more.`); empty → "No one has imported an RSI hangar yet". **`/hangar list`** appends `💰 <totals> pledged on ships across N pledges` before the editor footer. **Editor:** Import page "RSI hangar" section (HtfImport), RSI badge on ship cards/ship page (`RSI · LTI · <pledge> · $350.00`, else "Added manually"), the same total line on hangar views (details in `hangar-editor/README.md`). **sc-knowledge:** `sc_member_hangar` ship entries carry `rsi` (`pledgeName, pledgeDate, pledgeCost, lti, warbond, rsiName`) and the response passes `pledgeSummary` through; new read-only `sc_pledge_leaderboard()` returns the leaderboard JSON (same bounds/`unavailable` error as the other hangar tools). **Rollout gotchas:** re-run `scripts/registerCommands.js` from the bot pod (new `leaderboard` subcommand; registration replaces the whole set) and **restart the voice sidecar** (sc-knowledge declarations load once at startup); the agent sidecar picks the tool up automatically.

## Slots from fitted items

**Slots from fitted items, unlisted items, importer stock rule (since 2026-10-11).** Spec: `docs/superpowers/specs/2026-10-11-hangar-item-slots-design.md`. Origin: an F7C Hornet Mk II with a ball turret showed no guns and its nose slot had nothing to pick. Three causes, three fixes:
- **A fitted item brings its own slots.** A turret's gun ports belong to the turret ITEM (Wiki `v2/items/{uuid}` → `ports`), not the vehicle, and the stock F7C has a cargo module / an empty nose there. `Catalog.item_slots(uuid)` parses an item's ports with the same rule as vehicle ports; async `resolve_slots(catalog, vehicle_slots, fitted)` (`loadout.py`) builds the ship's ACTUAL slot list — for each fitted entry, parents first, the slots under it are replaced by the fitted item's ports (ids `<parent>/<itemPortName>`, flagged `dynamic: true` in the loadout). Bounds: `MAX_DYNAMIC_DEPTH` 4, `MAX_DYNAMIC_LOOKUPS` 16 per ship; a failed lookup on a READ means "no children", never an error. **Only slots that accept `Turret` trigger an item lookup** (`SLOT_BEARING_TYPES`): measured live, 88 of 242 Turret items have slot ports and 0 of 681 items of the other nine types do, and without the gate every fitted shield would cost a Wiki call behind the shared 60/min limiter — add a type there if another one ever grows ports. Every pairing of `catalog.slots(vehicle)` with a ship's `fitted` (hangar read, web/chat fit, reset, slot options, spviewer) goes through the resolver; `/catalog/vehicles/{uuid}/slots` stays stock.
- **Children when a parent changes:** after a fit or reset of slot `S` the service re-resolves and keeps a fitted entry under `S/` only if its slot still exists AND `check_compatible` still accepts its item; the rest are deleted in the same write and returned as `dropped: [{slot, item: {uuid, name}, reason: slot_removed|incompatible|unknown_item}]` (web fit/reset return `{ship, dropped}`; chat fit/reset also list them in `changes` with `dropped: true`). If the catalog cannot check the children the request is 503 and nothing is written.
- **Picker for such a slot:** `GET /catalog/slot-options?member=<id>&ship=<shipId>&slot=<id>` looks the slot up in that ship's resolved slots (`vehicle` is ignored in this form; `member` and `ship` must come together). The editor always sends them and keys its cache per ship.
- **The Wiki's item LIST omits items it knows by uuid** (the Hornet Mk II nose and ball turrets: `filter[sub_type]=CanardTurret` returns 0; name search misses them too). UEX lists them with the SAME uuids, so `Catalog._item_records` adds a **UEX supplement** per type: UEX `items?id_category=<n>` uuids absent from the Wiki list are fetched one by one from the Wiki (`UEX_CATEGORIES`: Turret 35, WeaponGun 32, MissileLauncher 33, Shield 23, Cooler 19, PowerPlant 21, QuantumDrive 22, WeaponMining 29, TractorBeam 67; cap `MAX_SUPPLEMENT_ITEMS` 40 per type; 12 h cache; measured 17 detail calls in total). It never fails a picker: a UEX or detail error logs a WARNING, serves the last good supplement (or the Wiki list alone) and retries after 10 min. Env `UEX_BASE` (default `https://api.uexcorp.uk/2.0`), optional `UEXCORP_BEARER` (never logged). A same-manufacturer vehicle scan was rejected: no ship carries the F7C's S2 nose turret as stock.
- **spviewer import: stock means the WIKI's stock.** spviewer rewrites a port's tree to the fitted item's ports and records its own "base" item (for the F7C centre: the C5-173f turret; nose: the S2 nose turret), which is not the Wiki's stock. The importer used to treat "equals spviewer's BaseLoadout" as unchanged, so it missed both turrets and skipped their guns as untracked. Now a port is unchanged only when its item is the stock item of the slot in the RESOLVED list (parents first, children checked against the item being fitted); `BaseLoadout` is only used to read spellings. Real fixture: `tests/fixtures/spviewer_f7c_mk2.json` (expected `fitted` asserted exactly). The Wiki item port names equal spviewer's child port names, so no mapping table exists or is needed.
- **Still not modelled:** required tags / port tags (a Hornet-only turret is offered for any slot of the right type, sub-type and size), missiles, and modules as a pickable type (the cargo module comes back only through reset to stock). Chat `hangar_fit` of a gun on a TMSB-5 answers `choose_slot` with four candidates (each gimbal port and the gun port inside it).

The editor side of this is in `hangar-editor/CLAUDE.md`.

## Limitations

**Limitations and future items:** Not built: **loose inventory** (items in storage, not fitted), **org-wide queries** ("who has a ship that fits a size-2 QD?"). The import doesn't model spviewer's required tags (e.g. `VanguardNose` guns) — the picker and fitting accept any compatible item of the right type/size. Missiles aren't tracked; sub-type rules apply only where the Wiki lists sub-types.
