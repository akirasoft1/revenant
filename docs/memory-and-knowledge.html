Field Guide · Memory & Knowledge

An agent without memory is just autocomplete.

Clovar gives every agent four overlapping systems for keeping track of what it has seen and what it has read: a graph for facts, a vector index for semantic recall, episodes for what happened, and a knowledge base for things people wrote down. Together they decide what the model gets to read before it answers you.

Read: nodes typed by kind — entity, decision, fact, topic — connected by free-text relations. The halo marks importance; the halo dims over time.
§ 01 · FOUR LAYERS, ONE PROMPT

Each layer remembers a different shape of thing.

"Memory" inside Clovar isn't one bucket. It's four distinct stores, each tuned for what it holds best. When the orchestrator assembles a turn, it queries all of them and merges the survivors into the system prompt. None of them runs in the model's head — every recall is a database query first.

Layer 01

The Graph

Nodes (facts, entities, decisions) joined by typed edges. Exact lookups, neighbor walks, importance decay.

postgres structured
Layer 02

The Index

Every node and every doc chunk has a vector. Semantic recall finds memories that mean what you asked, not what you typed.

qdrant semantic
Layer 03

Episodes

A background job clusters past messages into "what happened" summaries with key entities and importance scores.

async job narrative
Layer 04

Knowledge

Long-form documents that humans wrote — PDFs, markdown, URLs. Chunked, embedded, searchable per collection.

collections authored
The architectural choice

A pure vector store is fast but lossy — you can't ask "what did the agent decide about Acme?" and get a clean answer. A pure graph is precise but blind to paraphrase. The two layers complement each other; Clovar always consults both and lets the ranker decide which wins.

A vector index says "this feels related". A graph says "this is exactly related, in this way, with this strength". You want both. — The hybrid-recall principle
§ 02 · THE GRAPH

Nodes and edges, in plain Postgres.

A MemoryNode is a small typed record: what kind of thing it is, a label, a body of content, an importance score, and a counter of how often it's been retrieved. Edges are even simpler — a directed pair of node IDs with a free-text relation type and a strength.

The graph lives in two ordinary Postgres tables. There's no specialized graph database, no Cypher, no MATCH syntax. The richness comes from the access pattern rather than the storage: the recall service walks one hop out from any matched node and pulls neighbors into the result.

Importance isn't static. Every recall hit increments AccessCount and refreshes LastAccessedAtUtc. The ranker decays importance over 14 days and re-boosts whatever is touched. Memories that matter stay sharp; memories that don't fade.

§ 03 · HYBRID RECALL

Five channels, one ranked answer.

GraphMemoryService.RecallAsync runs five retrieval channels against the same query, deduplicates by content, and ranks by a temporal decay formula. The first time you read the order, it looks redundant — but each channel is catching a different kind of "relevant".

01
Vector searchmemory_nodes collection
Embed the query, search Qdrant for the nearest nodes. Catches paraphrase ("payment terms" → "net-30"). Results get a 1.2× boost.
×1.2boost
02
Label & content searchSQL ILIKE on nodes
Exact-text match against node labels and content. Catches names, IDs, and any literal token the vector might miss.
×1.0baseline
03

For each top-5 matched node, fetch its directly-connected neighbors. Pulls related context the query never named.
×0.7indirect

Search the episodic summaries for the same terms. Surfaces "we already talked about this on May 18th".
×0.9narrative
05
Summary lookup14 / 30 day window
Session-level (14d) and weekly (30d) summary rollups. Long-horizon context without rereading every message.

// Temporal-decay score: recent + accessed + important rises.
// Old, untouched memories drift down.

score = importance
      × exp(-λ × days_since_last_access)   // 14-day half-life
      × (1 + 0.1 × ln(access_count))
      × channel_weight                          // from the table above
Why the half-life matters

Without decay, a fact written six months ago about a deal that's long since closed would keep crowding out fresh context. The half-life isn't there to delete memory — it's there to downrank it so newer, more touched memories surface first. The old fact is still in the graph; the agent just stops thinking about it.

§ 04 · EPISODES

The agent's diary, written by a different model.

An Episode is a summary of a contiguous block of conversation, written asynchronously after the fact. The EpisodizationJob wakes up on a schedule, finds messages that haven't been processed, groups them by 30-minute inactivity gaps or session boundaries, then asks an LLM to produce a structured summary: what happened, who and what was mentioned, how important the conversation was.

What gets written

The job emits an Episode row plus a fan-out: links to every constituent message via EpisodeMessages, and any new MemoryNode / MemoryEdge rows it extracted (entities mentioned, decisions made, facts confirmed). The new nodes get SourceEpisodeId set so the graph stays provenance-traceable.

Why async, not inline

Episodization is expensive — an extra LLM call per conversation. Running it inline would double the latency of every turn. Running it as a background job keeps the user-facing turn fast and lets the system process episodes in batches when load is low.

What the agent sees

Recall surfaces episodes alongside nodes (channel 4 above). When the agent asks "what did we decide about Acme last week?", the episode summary often beats a stack of raw messages — it's compressed, it's labeled with key entities, and it includes the importance score the previous turn assigned.

§ 05 · KNOWLEDGE BASE

Documents in, searchable chunks out.

The knowledge base is the layer for things humans wrote — vendor catalogs, policy PDFs, internal handbooks, URLs the agent should know about. Documents arrive through three doors (a tool, a REST endpoint, or a file upload), get chunked, embedded, and indexed. From the agent's perspective they're just another retrievable source.

Chunk window
500words
Word-based sliding window. Not linguistic — splits on whitespace.
Overlap
50words
10% overlap preserves context across chunk boundaries.
Embedding dims
1 536
Default text-embedding-3-small. Configurable per business.
Search fallback
keyword
If Qdrant is down, KnowledgeService falls back to SQL term-count scoring.
Why keyword fallback exists

The vector store is a separate process and a separate network hop. When it's unavailable, knowledge retrieval doesn't fail — it degrades. The fallback scans indexed documents for the query's terms and returns a score of match_count / query_term_count. Worse than vectors, better than nothing.

§ 06 · WHERE MEMORY LANDS

The pre-call recall, in one block.

During turn composition (step 04 of the orchestrator's eleven-step assembly), the orchestrator picks a search query — usually the last user message — and calls RecallAsync. The returned memories are formatted into a Markdown block titled ## Memory Context and appended to the system prompt before any tool catalog or org context. 

injected · system prompt fragment
## Memory Context
[graph · decision] Approved PO-2401 for Acme
  Approved PO-2401 (Acme Mfg) on net-30 terms after CFO sign-off.
  → related: Acme Mfg (entity), net-30 (fact), vendors (topic)

[graph · fact] Acme prefers net-30 over net-15
  Confirmed in the May 12 vendor sync.

[episode · 2026-05-18] Reviewed PO-2401 for Acme
  Reviewed PO-2401 for Acme. CFO sign-off received. Approved on
  net-30 terms. Asked buyer-a to draft the vendor email.
  key entities: Acme Mfg, PO-2401, buyer-a, CFO

[knowledge · vendor-handbook.pdf] Acme · payment terms
  Acme Manufacturing operates on net-30 for orders above $50k.
  Orders under that threshold default to net-15 unless renegotiated.

// the agent reads this once, near the top of the prompt,
// before any tool calls are considered.

That single block is everything the model knows about prior context for this conversation. The retrieval is bounded (default top-10), the format is uniform, and each entry carries its provenance tag so the model can cite the source if it needs to.

§ 07 · ANTI-PATTERNS

Three things the memory layer is not for.

Don't use it as a database

Memory is for things the agent should consider when thinking. It's lossy, bounded, ranked, and decayed. If you need an authoritative record of every purchase order, write to your ERP — and let the agent remember that you wrote, not the full record. The graph stores the trail, not the system of truth.

Don't ingest the entire internet

Knowledge collections are powerful and expensive — every document is parsed, chunked, embedded, and indexed. Be deliberate about what goes in. A focused 50-document collection retrieves better than a 5 000-document mass; vector neighborhoods are crowded by noise.

Don't bypass the recall path

It's tempting to skip RecallAsync and stuff everything you know into the system prompt by hand. Don't. Recall ranks, dedupes, decays, and bounds — all the things that keep the prompt from blowing past the context window. Bypass it and you'll be chasing token-limit errors within a week.

Don't expect inline episode writes

Episodization runs on a background schedule. There's no guarantee that today's conversation will be summarized in time for tomorrow's first turn — and definitely not in time for the next turn in the same session. If you need immediate fact persistence, call memory-save explicitly from a tool; don't wait for the episodizer.
