# Hangar web editor (hangar.aklabs.io) — Design

**Date:** 2026-10-09 · **Status:** approved (brainstorming) · **Branch:** `feat/hangar-editor`
**Project 2 of 3** of the member hangar (project 1: `docs/superpowers/specs/2026-10-09-member-hangar-design.md`, shipped in PR #120). Project 3 = chat edits.

## Goal
A web page where members sign in with Discord and manage their Star Citizen hangar — the bulk-seeding path that `/hangar` is too slow for: add/rename/remove ships, fit components slot by slot from only-compatible items, reset to stock, view other members' hangars, and import saved loadouts from spviewer. Same data the bot's tools read (Firestore via `hangar-service`), so edits show up immediately in `/hangar list` and the bot's answers.

## Decisions
- **Architecture (mirrors the owner's home-build app):** `hangar.aklabs.io` → Cloud DNS zone (delegated by NS records the owner adds at the `aklabs.io` DNS provider) → static IP → global external HTTPS load balancer (`EXTERNAL_MANAGED`) with a Google-managed certificate; HTTP → HTTPS redirect. URL map: ALL paths → serverless NEG → the existing Cloud Run `hangar-service`, which also serves the built SPA (static assets with long-cache hashed filenames; any non-`/api`, non-`/v1`, non-`/health` GET that isn't a file returns `index.html` with `Cache-Control: no-cache` so client routes work). **Why not a GCS backend bucket like the home-build app:** that app's project has no parent organization; `revenant-discord-bot-2` is under an org whose domain-restricted-sharing policy blocks `allUsers` on buckets as well as Cloud Run, so a public bucket is impossible here without loosening the org policy. All in GCP project `revenant-discord-bot-2`, region `us-central1`. Scripted in `hangar-service/scripts/setup-domain.sh` (idempotent, pauses for the manual NS step, prints the records).
- **Cloud Run access:** the org's domain-restricted-sharing policy blocks `allUsers`, so `hangar-service` is updated with **`--no-invoker-iam-check`** (this service only; the org policy is untouched). The app's own authentication becomes the only gate: Google ID tokens (bot, sc-knowledge — unchanged, still via the `run.app` URL and the exact audience `https://hangar-service-hvmf2jpuca-uc.a.run.app`) and Discord sessions (browsers). Every `/v1` and `/api/v1` route stays authenticated; `/health` stays open.
- **Route prefixes:** existing routes are served at both `/v1/...` (service callers) and `/api/v1/...` (browser, through the LB). New browser-only routes live under `/api/`.
- **Discord OAuth2 (authorization-code, scope `identify`):** client ID `1558216042151419935` (env `DISCORD_CLIENT_ID`); client secret in Secret Manager `hangar-discord-client-secret`; redirect URI `https://hangar.aklabs.io/api/auth/callback`. Routes:
  - `GET /api/auth/login` → sets a short-lived signed `hangar_oauth_state` cookie (random state + optional `next` path, same-origin only) and 302s to Discord's authorize URL.
  - `GET /api/auth/callback?code&state` → verifies state, exchanges the code (`https://discord.com/api/oauth2/token`), fetches `GET https://discord.com/api/users/@me`, sets the session cookie, 302s to `next` or `/`. Any failure → 302 to `/?login_error=<code>` (never a stack trace).
  - `POST /api/auth/logout` → clears the session.
  - `GET /api/me` → `{discordId, username, globalName, avatarUrl, isAdmin}` or 401.
- **Session:** a signed (HMAC, itsdangerous-style, key from Secret Manager `hangar-session-key`) cookie `hangar_session` carrying `{discordId, username, globalName, avatar, iat}`; `HttpOnly; Secure; SameSite=Lax; Path=/`; max age 30 days; no server-side store. A Discord-session resolver joins the existing credential chain (`auth.py` `Authenticator`) and yields a principal whose **acting member is the session's Discord ID** (browser requests never send `X-Acting-Member`; the header is ignored for session principals). The write rule is unchanged: own hangar, or acting member ∈ `HANGAR_ADMIN_IDS`; reads of any member allowed.
- **CSRF:** writes from session principals require same-origin — `Origin` (or `Referer`) must be `https://hangar.aklabs.io` (`HANGAR_PUBLIC_ORIGIN`); plus the SameSite=Lax cookie. Service-token callers are unaffected.
- **Member directory (for "view others"):** `GET /api/v1/members` → members that have ≥1 ship: `[{discordId, shipCount, displayName?}]`. Display names come from the session user for self; for others the editor shows the Discord ID unless a name is known — the hangar service stores `ownerName` (Discord global name/username) on ship documents written through a session so the directory can show it. (The bot's `member_identities` registry lives in the cluster's Mongo and is not reachable from Cloud Run; out of scope.)
- **Item picker data:** `GET /api/v1/catalog/vehicles/{uuid}/slots` (existing) + new `GET /api/v1/catalog/slot-options?vehicle=<uuid>&slot=<slotId>` → compatible items for that slot (same compatibility rule as `check_compatible`: type ∈ compatibleTypes, sub-type rule, size in range), each `{uuid, name, type, size, grade, class, keyStat:{name, value, lowerIsBetter}, cheapestPrice?:{price, shop, location}}`. Key stat per type = the same per-type stat sc-knowledge's `sc_compare_components` ranks by (copy the small mapping into hangar-service with a keep-in-sync comment naming sc-knowledge's file). Shop prices from UEX `items_prices` (optional; the field is omitted when UEX is unavailable or the item is not sold — the picker still works).
- **spviewer import:**
  - The editor shows the export snippet (downloads `spviewer-loadouts.json` from spviewer.eu's IndexedDB `SCSPVDatabase` → `vehiclesLoadout`, all rows).
  - `POST /api/v1/import/spviewer/preview` (multipart or JSON body, ≤ 2 MB) → for each row: decode `loadoutData` (LZ-string `decompressFromEncodedURIComponent`; Python port `lzstring` or a small vendored decoder — tests pin it against the real fixture), resolve the vehicle (`vehicleClassName` → Wiki vehicle `class_name`), walk all `*Ports` recursively building slot ids by joining `PortName`s with `/`, and for each port whose id is a tracked hangar slot of that vehicle and whose `Loadout` differs from `BaseLoadout.ClassName`: resolve `Loadout` (a Wiki item uuid or a game class name) to a Wiki item and check compatibility. Response per row: `{rowIndex, loadoutName, vehicle:{uuid,name}|null, patch, changes:[{slot, from, to:{uuid,name}}], skipped:[{slot?, reason, detail}], matchingShips:[{shipId, label}]}`. Nothing is stored.
  - `POST /api/v1/import/spviewer/apply` `{rows:[{rowIndex, mode:"new"|"existing", shipId?, nickname?}], file}` → re-decodes server-side (never trusts client-sent changes), then creates the ship (mode new, nickname defaults to `loadoutName`) or applies to the existing owned ship; sets exactly the computed `fitted` overrides (slots not changed by the loadout are reset to stock for that ship — the import is authoritative for that ship) and returns the updated ships. Writes only to the acting member's own hangar (admins: target member query param, same rule).
  - Rows whose vehicle cannot be resolved, unknown/incompatible items, and untracked slots (missiles, paint, flair, flight controller, life support, untracked types) are reported in `skipped`, never silently dropped. A `loadoutData` that fails to decode or has an unexpected shape → that row is `skipped` with reason `unrecognized_format`.
- **Frontend (`hangar-editor/`):** React 18 + TypeScript + Vite + TanStack Query + React Router, built to static assets uploaded to the bucket with long-cache hashed assets and `no-cache` `index.html`. Pages: Login landing; My hangar (ship cards; add ship with catalog search; rename; remove with confirm); Ship detail (slot table grouped by type: slot, size, current item, stock/fitted badge; "Change" opens the compatible-item picker sorted by key stat with price; "Reset to stock"); Members (directory → read-only hangar, admins get edit); Import (snippet with copy button, upload, per-row preview with mode/ship selection, apply, result summary). Mobile-friendly. Dynatrace RUM snippet included via an env-configured script tag (empty = disabled).
- **Deploy/versioning:** the SPA is built inside the hangar-service image (multi-stage Dockerfile: node build stage → `hangar-editor/dist` copied into the Python image), so one image tagged with the git short SHA ships API + editor together; `/version.txt` carries the SHA. No `:latest`. The image build context becomes the repo root with a hangar-service-specific dockerignore so no secrets or other services are included.
- **Bot:** `/hangar list` reply gains a footer line "Edit in the browser: https://hangar.aklabs.io" (config `HANGAR_EDITOR_URL`, omitted when unset).

## Security notes
Secrets only in Secret Manager (`hangar-discord-client-secret`, `hangar-session-key`) read by the runtime SA `hangar-runtime@` (granted `roles/secretmanager.secretAccessor` on both); the local `.env_sc_hanger` is git- and docker-ignored. Session cookies are signed, not encrypted — they contain only public Discord profile fields. OAuth `state` prevents login CSRF; same-origin checks protect writes. Upload size capped; decoder output size capped (e.g. 2 MB decompressed per row) to avoid decompression bombs. Logs never contain tokens, cookies, codes or secrets — and are never truncated.

## Testing
- **hangar-service (pytest):** OAuth login/callback with a fake Discord (state mismatch, token error, user fetch error, success sets cookie); session sign/verify/expiry/tamper; session resolver in the chain (acting member = session id; header ignored); CSRF same-origin on writes; dual prefixes; members directory; slot-options compatibility + key stat + price-optional; spviewer decode against the real Harbinger export fixture (`tests/fixtures/spviewer_harbinger.json`, all-stock → zero changes) plus a synthetic modified loadout (changed QD + changed nose gun via uuid + a missile change → skipped untracked + unknown item → skipped); apply new/existing, authoritative reset, permissions, size caps.
- **SPA (Vitest + Testing Library):** slot picker filters/sorts, import preview renders changes/skips, auth gating.
- **Live:** `setup-domain.sh` run, certificate ACTIVE, `https://hangar.aklabs.io/health`-through-LB check, login with Discord, add/fit/reset, import the owner's export, confirm via `/hangar list` and the bot's `sc_member_hangar`.
