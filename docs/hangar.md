# Member hangar — tools, prompting, chat edits, `/hangar`

Moved verbatim from the root `CLAUDE.md` on 2026-10-12 to keep that file small. This file covers the hangar code that lives OUTSIDE `hangar-service/`, `hangar-editor/` and `tools/wireframes/` (each of those has its own `CLAUDE.md`). Nothing loads this file automatically: read it before changing hangar code in `sc-knowledge/`, `agent-sidecar/`, `voice-sidecar/`, `commands/slash/HangarCommand.js` or `services/HangarClient.js`.

The rules that hold everywhere are in the root `CLAUDE.md` "Member hangar".

## Credentials in the cluster

**Credentials in the cluster:** SA `hangar-api@` (no project roles; it only mints ID tokens for itself) — its JSON key lives ONLY in Secret `hangar-api-sa`, mounted read-only at `/var/secrets/hangar/key.json` in all four callers: the **bot** (`/hangar`), **sc-knowledge** (read tools), and the **agent** and **voice** sidecars (chat edits). All four run as uid 1000, which must be able to read the file (default secret mode 0644 works; `defaultMode: 0400` breaks it — the caller then answers `unavailable` with a WARNING naming the path). Callers' env: `HANGAR_API_URL` (= the audience URL in the root `CLAUDE.md` "Member hangar") and `HANGAR_SA_KEY_PATH` (default `/var/secrets/hangar/key.json`). Minting calls Google's token endpoint, so every caller pod — including the agent and voice sidecars — needs NetworkPolicy egress to `oauth2.googleapis.com` and `*.run.app` on 443. **Key rotation needs pod restarts** — every caller builds its credentials once and caches them. Both the agent and voice sidecars prewarm their ID token at startup (background, never raises), so the first edit doesn't pay for the mint.

## Tools (sc-knowledge)

**Tools (sc-knowledge, so text and voice both get them):** `sc_member_hangar(member_id, ship=None)` (ship resolved within that member's hangar: exact nickname → nickname fuzzy → exact model → model token/prefix with a small shorthand table, "Connie" → Constellation → model fuzzy; ambiguous → candidates) and `sc_member_fit_check(member_id, item)` (per-slot `upgrade`/`downgrade`/`sidegrade` (≤2% on the key stat `sc_compare_components` ranks by)/`same`/`unknown`, plus `not_compatible` ships with `size_mismatch`/`no_slot`/`loadout_unavailable`). UC1 = `sc_member_hangar` + `sc_compare_components(purchasable_only=True)`. The sc-knowledge client is **read-only** (only `GET …/hangar`, never `X-Acting-Member`; a test pins it), token + request bounded at 3s, responses cached 30s, and each tool has a **5s overall deadline** under voice's 6s bound. A hangar outage returns `error("unavailable")`, never raises, never fails a turn. **`compatibleTypes` parity rule:** sc-knowledge's fit check applies the SAME compatibility rule as hangar-service's `check_compatible` (type in the slot's `compatibleTypes`, sub-types only when the slot lists some and the item's isn't `UNDEFINED`, size in range) using the `compatibleTypes` hangar-service puts on every loadout slot — change one, change both.

## Prompting

**Prompting — tool-called, never injected:** ship data is never put in the prompt. One sentence (`SC_HANGAR_RULE` in `agent-sidecar/src/agent.py`, both `web_search` variants; a short spoken version in voice `SC_VOICE_NOTE`) says: use the hangar tools only when the question is about a member's own ships or loadouts, never bring up anyone's ships unprompted, `member_id` is the numeric Discord ID from the `[Name · id]` labels or the "People in this conversation" roster, "my" = the labelled speaker. Voice has no per-turn id labels (Live audio) — the session opener is the roster's current speaker. **Voice limitation:** the roster is built once at session open, so a later speaker named only by a `[SPEAKER: name]` marker may not be in it — their "my" can't be resolved to a Discord ID, so the hangar tools can't be called for them (same mid-session-newcomer gap as the identity roster; nothing in the prompt handles it yet). The sc-unavailable note says hangars can't be looked up either (names no tool). `_SC_UNCOVERED` says "stock vehicle loadouts" with a pointer to the hangar tools, so the ordered fallback's step (2) never routes a member's own loadout question to google_search. Eval: four hangar cases in `agent-sidecar/eval/sc_eval_set.py` against the real service with fake members seeded by `eval/seed_hangar_eval.py --seed/--cleanup` (run in the sc-knowledge pod — the bot image has no Python), scored on the `member_id` argument, plus an `unprompted_hangar_calls` gate over every other case and a soft UC1 flag when no `sc_compare_components(purchasable_only=True)` follows the hangar call (see `agent-sidecar/eval/README.md`).

## Chat edits

**Chat edits — text AND voice (project 3, since 2026-10-09).** Spec: `docs/superpowers/specs/2026-10-09-hangar-chat-edits-design.md`. Members record changes by saying what they DID — "I put the Hemera in my Connie", "I just bought a Cutlass Black", "I put my Harbinger's shields back to stock" — or by explicitly asking to update their OWN hangar ("put my Harbinger's shields back to stock", "mark my Connie as having a Hemera"), and the bot writes at once and says what changed ("Connie's quantum drive: Bolon → Hemera"). No pending-confirmation store.
- **Tools (same names/semantics on both surfaces):** `hangar_fit(ship, item, slot=None)` → `POST /v1/members/{id}/fit`; `hangar_add_ship(vehicle, nickname=None)` → `POST /v1/members/{id}/ships`; `hangar_reset(ship, slot)` → `POST /v1/members/{id}/ships/{shipRef}/reset` (`slot` required: a hint, or `"all"` for the whole ship — the model asks if the user didn't say). hangar-service does ALL resolution server side: ship text within the member's own hangar (same resolver as `sc_member_hangar`, `src/ship_resolve.py`, KEEP IN SYNC), item text by catalog (exact, then fuzzy — "hemera qd", "lorica shields"; responses carry the canonical `item.name` and `item.matchedBy: "exact"|"fuzzy"`), slot hints ("left", "nose", "2", "shields", "all"). Errors are the service envelope handed to the model verbatim: 409 `ambiguous` + `field` (`"ship"`|`"item"`) + `candidates`, 409 `choose_slot` + `slots`, 404 `not_found` (+ `owned` for a ship, `suggestions` for an item), 422 `incompatible` + `reason` (`size_mismatch`|`no_slot`), `forbidden`, `unavailable`, `invalid_request`. Endpoint details: `hangar-service/README.md` "Chat edits". Each tool: 5s (token mint + request), never raises, writes send `X-Acting-Member`.
- **Binding rule — the acting member is supplied by trusted plumbing, NEVER a tool argument.** No tool has a member parameter, so "put a Hemera in Micro's Titan" can only touch the speaker's own hangar (and the model is told to say chat edits only apply to your own hangar). **Text:** `ChatRequest.user_id` (the Discord ID the bot sends for the turn's author), bound into the per-turn tool instances (`agent-sidecar/src/hangar_edit.py` `HangarEditTools`, same pattern as `RunInSandboxTool(user_id=…)`). **Voice:** the current floor holder's Discord ID from `SetSpeaker.user_id`, tracked per session in the sidecar (`live_bridge._SpeakerIdentity` on `_SessionRef`, preserved across reconnects) and bound when the tool call ARRIVES (a speaker change while the write runs can't redirect it); before the first SetSpeaker, `SessionStart.user_id` (the opener). **The bot sends SetSpeaker on EVERY floor-holder change** — id-only (`{userId, displayName: ''}`) when the speaker's name hasn't resolved, then once more with the name when it does (`VoiceService._handleUserPcm`, `g.lastSpeakerNameSent`). The sidecar's identity follows `user_id` ALONE: a non-empty id sets it (an empty `display_name` just means no `[SPEAKER:]` marker); only an empty `user_id` (the Phase 4 floor-release clear) clears it, and then the opener fallback does not come back. Why both halves: grpc-js reports a failed write asynchronously, so the release's clear can be lost — previously a nameless next holder sent nothing and edits stayed bound to the PREVIOUS holder. Empty/non-numeric id → `{error: "unknown_speaker", message: "I can't tell who's speaking, so I can't edit a hangar right now — use text chat or the web editor."}` without calling the service. Admins get no cross-member chat edits — they use the web editor.
- **Prompt (one short sentence each):** agent `SC_HANGAR_EDIT_RULE` inside `sc_tools_preamble` / `sc_tools_unavailable_note` (both `web_search` variants, only on turns the tools are attached); voice `HANGAR_EDIT_NOTE`, appended exactly once per session whenever the declarations are attached, with or without the sc_* tools (beside `SC_VOICE_NOTE` or the standalone `SC_MECHANICS_VOICE_NOTE`). Rule: call the edit tools ONLY when the speaker says they DID something to their own ships or explicitly asks to update their own hangar; never for advice/hypothetical questions ("should I…", "would X be better…"); on `choose_slot`/`ambiguous` ask a short follow-up (voice: at most three options spoken); after a write state what changed using the canonical item name returned; after a `maybe_applied` result don't repeat the write (never `hangar_add_ship` again) — check with `sc_member_hangar` first (voice without sc_* tools: say it may have saved and to check); only the speaker's own hangar.
- **`maybe_applied` (timeouts after commit):** every tool is a write, so a timeout or cancellation AFTER the request went out can't tell whether it landed. The result is `{error: "unavailable", maybe_applied: true, message: "The hangar service didn't answer in time — the change may have been saved; check before retrying"}` — returned for a timeout after the request went out, ANY other failure once the request was handed to httpx except a connect error (RemoteProtocolError, ReadError, read/write timeouts, …), and a non-JSON 5xx (a gateway 502/504 from Cloud Run/the LB; a 5xx carrying the app's own `{error,…}` envelope passes through). A failure before anything was sent — token mint, connect — is a plain `unavailable`. Same rule on both sidecars. Voice: the 6s bridge bound returns it too; a call the model cancels can't be answered, so the sidecar logs it as `-> cancelled, maybe_applied`. A blind retry of `hangar_add_ship` would add a second ship — that's why the prompt forbids it.
- **Voice plumbing:** local Live tools like `end_conversation`/`go_quiet` — declared in the SAME `Tool(function_declarations=…)` (order: control, hangar, sc_*), answered in-sidecar (never the MCP executor; a `hangar_*` call with edits off is `unknown_tool`), run as a task off the audio pump with a 6s total bound (`HANGAR_CALL_TIMEOUT_S`), FunctionResponse sent to the CURRENT Live session only (a late result after a reconnect is dropped and logged — the write itself still happened). Connect fallback: they ride the control layer — kept when the sc_* declarations are dropped, dropped together with the control tools on the second step (also when control tools are off but edits are on).
- **Flags/credentials:** `HANGAR_API_URL` (exactly `https://hangar-service-hvmf2jpuca-uc.a.run.app`, also the token audience), `HANGAR_SA_KEY_PATH` (default `/var/secrets/hangar/key.json`, Secret `hangar-api-sa`), `HANGAR_EDITS_ENABLED` (default true when `HANGAR_API_URL` is set; can only turn edits off) — on the **agent** and **voice** sidecars. **On the text agent it does nothing unless `SC_KNOWLEDGE_ENABLED=true`:** the edit tools and their prompt sentence only attach on turns where an SC note is in play. Voice attaches them independently of sc-knowledge. `hangar-api@` is already an allowed caller.
- **Logs/telemetry (never truncated, never tokens):** agent: INFO `hangar edit: tool=… member=… args=… result=… changes=…` per call and `agent.chat` span attr `hangar.edits`; voice: INFO `voice: hangar edit <tool> id=… member=<id> ship=… item=… vehicle=… slot=… -> <ok|error code> (<ms>ms) [ship_label=…] [changes=[slot: from -> to; …]] [maybe_applied=True] [message=…]` per call (`-> cancelled, maybe_applied` for a cancelled call), `hangar_edits=N` appended LAST on the `voice: session END` line and `voice.hangar_edits` on the `voice.session` span. Both count only writes that changed something (no error, not `unchanged`). hangar-service logs `hangar: chat fit:` / `hangar: chat reset:` per changed slot.

## `/hangar` (bot)

**`/hangar` (bot, `commands/slash/HangarCommand.js` + `services/HangarClient.js`):** `list [member]`, `add ship [nickname] [member]` (catalog autocomplete), `rename ship nickname [member]`, `remove ship [member]` (both autocomplete from the target's hangar). Ephemeral, deferred before any call. `list` is open to everyone for any member (reads are allowed by design); edits are self-only unless the invoker is a bot admin — the bot refuses first and the service re-enforces via `X-Acting-Member`, which `HangarClient` always sets to the invoking user. `HangarClient` never throws (`{ok:false, error}`), one 5s deadline covers token mint + fetch. Outage → "Hangar service is unavailable right now." **Registered only when `HANGAR_API_URL` is set — including in the environment that runs `scripts/registerCommands.js`:** registration replaces the whole command set, so running it without `HANGAR_API_URL` silently DROPS `/hangar` (it logs a WARNING). Run it from the bot pod. Autocomplete for rename/remove can come back empty while the catalog is cold (a lighter endpoint is a possible follow-up). **`/hangar list` ends with "Edit in the browser: <url>"** when `HANGAR_EDITOR_URL` (`config.hangar.editorUrl`, production `https://hangar.aklabs.io`) is set — also on the empty-hangar reply; the footer's length is reserved before the "…and N more" truncation so the reply stays ≤ 2000 chars. Unset = no footer.

The `/hangar leaderboard` subcommand, the pledge total line on `/hangar list` and the `sc_pledge_leaderboard` tool are described with the RSI import in `hangar-service/CLAUDE.md`.
