# Member hangar

Moved from the root `AGENTS.md` on 2026-11-11 so that file stays under the 24 KB per-file limit some agents enforce. Claude Code imports this file through the root `CLAUDE.md`; other agents should read it before changing any hangar code.

### Member hangar (per-member ship loadouts, since 2026-10-09)

Each member's Star Citizen ships and what is fitted in them, answered by tool in text AND voice: "what's a purchasable upgraded shield for my Harbinger?" (UC1), "I just looted a Hemera quantum drive, is it a usable upgrade for any of my ships?" (UC2), "I can't use this Hemera, can Micro?" (UC2b), "what's on my Connie?" (UC4).

**The service is NOT in this repo.** `hangar-service` (FastAPI on Cloud Run), the web editor at `https://hangar.aklabs.io`, and their infrastructure moved to the separate private repo `akirasoft1/sc-hangar` (GCP project `aklabs-sc-hangar`) in November 2026. The ship-wireframe pipeline moved to the private repo `akirasoft1/sc-gamedata`. The old deployment in `revenant-discord-bot-2` was deleted on 2026-11-21. This repo holds only the **callers**: the bot's `/hangar` command (`commands/slash/HangarCommand.js`, `services/HangarClient.js`), sc-knowledge's read tools, and the agent and voice sidecars' chat-edit tools. Service internals (data model, slot rules, org visibility, the web editor) are documented in sc-hangar. Changes to the contract below (API shape, token audience, `X-Acting-Member`, error envelope) must be made in both repos together.

**Where the detail lives:** `docs/hangar.md` covers credentials, the sc-knowledge hangar tools, prompting, chat edits (agent and voice sidecars) and `/hangar`. **Nothing auto-loads it:** read it before touching hangar code in `sc-knowledge/`, `agent-sidecar/`, `voice-sidecar/`, `commands/slash/HangarCommand.js` or `services/HangarClient.js`. The 2026-10 design specs and plans in `docs/superpowers/` are history and describe the service as it was in this repo.

**Client contract (rules that hold everywhere):**
- **URL and token audience are both exactly `https://hangar.aklabs.io`** (no trailing slash). It is the only audience the service accepts; a token minted for a `run.app` URL is a 401. Health is `/health`.
- **Credentials:** every caller reads the credential file at `HANGAR_SA_KEY_PATH` (default `/var/secrets/hangar/key.json`) and its `type` picks the flow. **Production uses `external_account` (Workload Identity Federation):** ConfigMap `hangar-wif-credentials` (no secret material) is mounted at `/var/secrets/hangar`, and a projected service-account token (audience = the WIF provider, 3600 s) is mounted at `/var/run/secrets/hangar-wif/token`. The caller exchanges that token at STS and calls `generateIdToken` on `hangar-caller@aklabs-sc-hangar.iam.gserviceaccount.com` with the email claim. That is ONE impersonation hop, and the federated principal (namespace `discord-article-bot`) holds only `roles/iam.serviceAccountOpenIdTokenCreator`. A `service_account` JSON key is still supported by the code, but no key exists any more; the old `hangar-api@` SA and Secret `hangar-api-sa` were deleted. Caller pods need egress on 443 to `sts.googleapis.com`, `iamcredentials.googleapis.com` and the hangar load balancer. The file must be readable by uid 1000. Credentials are built once and cached, so a credential change needs pod restarts. If the cluster's service-account signing key rotates, re-run `infra/setup-wif.sh` in sc-hangar.
- **Org binding:** `hangar-caller@` is bound to the org `cAd` on the service. A caller sees only members who share an org with it, plus the acting member. A member outside cAd is a 404 (`"no such member"`), the same as an unknown member.
- **Error envelope:** `{error, message, …}` with codes such as `not_found`, `ambiguous`, `choose_slot`, `incompatible`, `forbidden`, `unavailable` and `invalid_request`. Callers hand it to the model verbatim and never throw (`unavailable` on outage).
- **`X-Acting-Member`:** writes send the member the edit is for. `/hangar list` sends the invoker on reads, so the invoker sees their own hidden ships. sc-knowledge sends none. The service treats this header as trusted plumbing, so send only the invoking user's ID.
- **The acting member of a chat edit is supplied by trusted plumbing, NEVER a tool argument** (text: `ChatRequest.user_id`; voice: `SetSpeaker.user_id`, else the session opener). No cross-member chat edits, admins included.
- **Every chat edit tool is a write:** a `maybe_applied` result must not be retried blindly (a second `hangar_add_ship` adds a second ship).
- **Ship data is tool-called, never injected into a prompt.** The sc-knowledge hangar client is read-only (a test pins it).
- **Keep-in-sync pairs (the other half is in sc-hangar):** sc-knowledge's fit check ↔ hangar-service `check_compatible` (`hangar-service/src/catalog.py`); the ship resolver in `sc_member_hangar` ↔ `hangar-service/src/ship_resolve.py`; `SLOT_TYPES` ↔ `hangar-service/src/catalog.py`.
- **`scripts/registerCommands.js`:** run it from the bot pod. Registration replaces the whole command set, so running it without `HANGAR_API_URL` silently DROPS `/hangar`. A new subcommand needs a re-run; a new sc-knowledge tool needs a voice sidecar restart (declarations load once at startup).
- **No pledge costs or pledge leaderboard:** they were removed from the bot, its tools (`sc_pledge_leaderboard` is gone; `sc_member_hangar` never returns `pledgeCost`/`pledgeSummary`) and `/hangar` (no `leaderboard` subcommand). Do not reintroduce them.
- **HARD RULE: extracted game data never enters the repo or an image.** `.glb` exports, `.swf.gz` bundles, anything derived from them, and HangarXPLOR `shiplist.json` exports (personal pledge data) stay on the owner's machine and in the private model store. **Docker ignore patterns are root-anchored (unlike gitignore): a bare `*.glb` only matches the context root.** So the root `.dockerignore` (the bot image, `COPY . .`, PUBLIC) carries `**/*.glb`, `**/*.swf.gz` and `**/shiplist.json`, and `.gitignore` ignores them too. Keep those patterns even though the pipeline has left this repo. Never add a real export, or anything derived from one, as a fixture, and never force-add. **Why:** this repo and its Docker Hub images are PUBLIC; the owner accepts the licensing risk of using extracted geometry only for a private, Discord-gated site, not for redistribution.
