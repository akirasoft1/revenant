# Discord Article Bot - Development Guidelines

## Feature Development Workflow (TDD + Build + Deploy)

When implementing new features or fixes, follow this complete workflow:

### 1. Create Feature Branch
```bash
git checkout main && git pull origin main
git checkout -b feat/<feature-name>
# or fix/<issue-name> for bug fixes
```

### 2. TDD: Write Tests First (Red Phase)
- Write failing tests in `__tests__/` that define expected behavior
- Run tests to confirm they fail: `npm test -- --testPathPatterns="<TestFile>"`
- Tests should cover: happy path, edge cases, error handling

### 3. Implement Feature (Green Phase)
- Write minimal code to make tests pass
- Run tests frequently to verify progress
- Commit checkpoints with descriptive messages

### 4. Refactor (if needed)
- Clean up implementation while keeping tests green
- Ensure code follows existing patterns in codebase

### 5. Run Full Test Suite
```bash
npm test
```
All tests must pass before proceeding.

### 6. Update Documentation
- Update `features.md` with new capabilities
- Update `README.md` if user-facing features changed
- Update `CLAUDE.md` if development practices changed

### 7. Commit Changes
```bash
git add -A
git commit -m "feat: <description>

<detailed explanation>

🤖 Generated with [Claude Code](https://claude.com/claude-code)

Co-Authored-By: Claude Opus 4.5 <noreply@anthropic.com>"
```

### 8. Bump Version
```bash
npm version patch --no-git-tag-version  # for fixes
npm version minor --no-git-tag-version  # for features
git add package.json package-lock.json
git commit -m "chore: bump version to <version>"
```

### 9. Build and Push Docker Image
```bash
docker build -t mvilliger/discord-article-bot:<version> .
docker push mvilliger/discord-article-bot:<version>
```

### 10. Deploy to Kubernetes
```bash
kubectl set image deployment/discord-article-bot bot=mvilliger/discord-article-bot:<version> -n discord-article-bot
kubectl rollout status deployment/discord-article-bot -n discord-article-bot --timeout=120s
```

### 11. Verify Deployment
```bash
kubectl get pods -n discord-article-bot
kubectl logs -f deployment/discord-article-bot -n discord-article-bot
```

### 12. Push Branch and Create PR
```bash
git push -u origin feat/<feature-name>
# Create PR via GitHub (gh auth may be expired)
```

### Checkpoint Commits
For larger features, commit checkpoints along the way:
- After tests are written (even if failing)
- After major implementation milestones
- Before risky refactoring

## Important Notes
- **Development Methodology**: Follow Test-Driven Development (TDD) practices. Write tests before implementing features or fixes.

## Deployment

- **Namespace**: Always deploy to `discord-article-bot` namespace, not `default`
- **Container name**: The deployment container is named `bot`, not `discord-article-bot`
- **Source of truth**: `k8s/overlays/deployed/` (gitignored, contains real secrets)
- **Do NOT use kustomize**: The `k8s/base/` and `k8s/overlays/prod/` are out of sync and contain placeholder secrets

### Deployment Steps

1. Build and push Docker image:
   ```bash
   docker build -t mvilliger/discord-article-bot:<version> .
   docker push mvilliger/discord-article-bot:<version>
   ```

2. Update image version in `k8s/overlays/deployed/deployment.yaml`

3. Apply the deployment:
   ```bash
   kubectl apply -f k8s/overlays/deployed/ -n discord-article-bot
   ```

   Or for image-only updates:
   ```bash
   kubectl set image deployment/discord-article-bot bot=mvilliger/discord-article-bot:<version> -n discord-article-bot
   ```

4. Verify rollout:
   ```bash
   kubectl rollout status deployment/discord-article-bot -n discord-article-bot
   ```

### NetworkPolicy Configuration

**IMPORTANT**: This namespace uses a restrictive NetworkPolicy that blocks egress to private IP ranges by default.

When adding a new external service integration (especially services on local/home network IPs like `192.168.x.x`, `10.x.x.x`, `172.16.x.x`):

1. **Update the NetworkPolicy** in `k8s/overlays/deployed/networkpolicy.yaml`
2. Add an egress rule for the specific IP and port:
   ```yaml
   # Example: Allow Local LLM (Ollama) on home network
   - to:
       - ipBlock:
           cidr: 192.168.1.164/32
     ports:
       - protocol: TCP
         port: 11434
   ```
3. Apply the change: `kubectl apply -f k8s/overlays/deployed/networkpolicy.yaml -n discord-article-bot`
4. Restart the pod to re-initialize the service

**Debugging connectivity issues**:
```bash
# Check current NetworkPolicy
kubectl get networkpolicies -n discord-article-bot -o yaml

# Test connectivity from a fresh pod (no NetworkPolicy restrictions)
kubectl run test-curl --rm -it --image=curlimages/curl -- curl http://<ip>:<port>/endpoint
```

## Voice Profile (Channel Voice Personality)

The `channel-voice` personality dynamically learns the group's communication style from IRC history and Discord messages. It requires:
- `VOICE_PROFILE_ENABLED=true`
- Qdrant service enabled (for IRC history sampling + few-shot retrieval)
- Channel Context service enabled (for Discord message sampling)

**Config env vars**: `VOICE_PROFILE_REGEN_HOURS`, `VOICE_PROFILE_SAMPLES_PER_DECADE`, `VOICE_PROFILE_DISCORD_SAMPLES`, `VOICE_PROFILE_ANALYSIS_MODEL`, `VOICE_PROFILE_AB_LOGGING`

**A/B logging**: Set `VOICE_PROFILE_AB_LOGGING=true` to log styled vs. unstyled response comparisons to the `ab_comparisons` MongoDB collection.

**Profile storage**: MongoDB `voice_profiles` collection. Versioned with `previousVersion` for history.

## Recall (v2 centralized ranked recall)

`RecallService` (`services/RecallService.js`) replaces the scattered Mem0 + channel-context recall when `RECALL_V2_ENABLED=true`. It over-retrieves from all sources, dedupes, ranks by recency+importance (Mongo `recall_ledger` holds importance/access/last-access), and injects one `## Memory Context` block. Pure logic in `services/recall/` (ranking, queryBuilder, adapters, evalMetrics).

- **Validate before flipping on**: run `node scripts/eval-recall.js` (offline ranker eval) and enable `RECALL_SHADOW_ENABLED=true` to log old-vs-new to `recall_comparisons`.
- Recent buffer + voice few-shot are intentionally NOT ranked (separate blocks).
- Spec: `docs/superpowers/specs/2026-05-30-centralized-ranked-recall-design.md`.

## Agentic Sandbox

When `AGENT_ENABLED=true`, channel-voice chats are routed through the Python agent sidecar (`discord-article-bot-agent`). The sidecar is an ADK Agent with one tool — `run_in_sandbox` — that spawns ephemeral pods per execution and returns `{exit_code, stdout, stderr, duration_ms, egress_events, runtime_events}` to the model. Other personalities are unaffected.

**Chat context (unified):** Both the text agent path (`ChatRequest`) and voice Live path (`SessionStart`) forward the same three context fields to the sidecar:
- `system_prompt`: the dynamic channel-voice personality with `{VOICE_INSTRUCTIONS}` substituted from the live voice profile
- `memory_context`: the ranked `RecallService` block (Mem0 + channel semantic + channel facts, deduplicated and ranked by recency + importance)
- `history`: recent conversation turns as `[{role, content}, ...]`, sourced bot-inclusively from `MongoService.getRecentChannelMessages` (the `channel_messages` MongoDB collection)

`channel_messages` is the ONLY history source, so **every chat entry point records both sides of its exchange there** with the same doc shape (shared writers in `utils/channelMessageRecorder.js`): @mention and reply — the user message via bot.js's `messageCreate` recorder, the bot reply via `_recordBotReply`; `/chat` — a slash interaction is not a channel message (messageCreate never sees it), so `ChatCommand` records the prompt itself (`messageId` = interaction id, guild-only like messageCreate) *before* calling chat, awaited so `buildTurnContext`'s `_dropDuplicatedCurrentTurn` removes it and the current turn reaches the model once, then the raw model reply (`isBot`, `executionIds`). Before this, a `/chat` Q&A was invisible to every later turn. **Discord replies name their referenced bot message on the current turn:** the reply fall-through (`bot.js` `_handleReplyToBot` → `_handleMentionChat` → `ChatService.chat(..., { referencedMessage })`) hands `buildTurnContext` the replied-to bot message, and on EVERY such turn (non-empty after stripping the fallback banner / `<url>` wrapping) it returns `currentTurn` = `[Replying to your earlier message: "<full referenced text>"]\n<userMessage>`, which `chat()` sends as the agent's `userMessage` (full text, never truncated). History is left chronological and untouched. Why not window position: the old rule appended the target as an assistant turn only when it was OUT of the window and was a no-op otherwise — in the 2026-09-29 incident the replied-to Levski answer WAS in the window, followed by a newer, unrelated Ruin Station question from another user, so "are they unique…?" was resolved to Ruin Station. Moving the target next to the current turn was rejected too: after a newer question it reads as the answer to *that* question. The prefix is applied AFTER `_dropDuplicatedCurrentTurn` (which compares the raw text), and stored `channel_messages` content and recall queries stay raw. If `buildTurnContext` throws, the degraded path sends the raw `userMessage` (no prefix). This also covers replies to `/chat`'s interaction replies. Agent path only — the direct-OpenAI fallback does not use it.

**Who-said-what labels + roster (member identity, since 2026-10-09):** `buildTurnContext` labels every non-bot history turn `[<Name> · <discordId>]: <content>` (middle dot U+00B7) and prefixes the current turn with the current speaker's label (composed under the reply prefix: `[Replying to …]\n[Name · id]: <message>`), so "I/me/my" resolve to the labelled speaker instead of the model guessing from first-person text. Bot (`isBot`) turns and rows without an `authorId` stay unlabelled. **Naming order for a label:** registry `addressName` → latest stored `authorName` → `VOICE_SPEAKER_NAMES`/Discord names (`SpeakerNames`) → registry alias → `Unknown`. **Labelling happens AFTER the raw dedupe** (`_dropDuplicatedCurrentTurn` still compares raw text; stored `channel_messages` content and recall queries stay raw). A `## People in this conversation` roster block is appended to the returned `systemPrompt`: current speaker first (marked `← current speaker`), every distinct `authorId` in the history window, plus any registry member whose addressName/alias appears as a whole word (case-insensitive, Unicode-aware boundaries, so alias `Aki` does not match inside `Akirasoft`) in the window or current message; cap 20, never the full table, omitted when empty; the block's instruction (`ROSTER_INSTRUCTION`) says "I/me/my" mean the labelled speaker, to use the list only to work out who is who, not to mention aliases unless it matters, and never to start its own replies with a label. **Failure isolation:** registry lookups are in-memory and never throw into a turn; if the registry failed to load, labels fall back to stored `authorName` and the roster lists resolved names only. Origin: an incident where the model answered another user's "Akira, …" as if it were the asker. Spec: `docs/superpowers/specs/2026-10-09-member-identity-design.md`.

Built by one shared method: `ChatService.buildTurnContext({...}) -> { systemPrompt, memoryBlock, historyTurns }`. The sidecar runs the bot's `system_prompt` (generic `base.txt` is fallback-only when `system_prompt` is empty). The sandbox executor itself still receives no memory or history — context is injected at the model turn only, not the tool layer. `run_in_sandbox` remains a last-resort tool gated by `TOOL_AVAILABILITY_PREAMBLE`. Note: sidecar `requirements.txt` floors track the current releases (raised 2026-09-26; both sidecars run `python:3.14-slim`). **Agent-sidecar holdback:** google-adk ≥2.8 caps OpenTelemetry at ≤1.42.1, which needs protobuf <7, and every grpcio-tools newer than 1.81.1 needs protobuf 7 — so the agent sidecar runs protobuf 6.33 / grpcio-tools 1.81.1 / OTel 1.42.1 (stubs regenerated to match). Raise all three together once adk lifts its OTel cap. The voice sidecar has no adk and runs protobuf 7.x.

**Token-trim split (deliberate, not DRY debt):** `buildTurnContext` forwards `memoryBlock`/`historyTurns` to the unified agent path UNTRIMMED — no legacy `config.recall.promptMaxTokens` cap — because Gemini's ~1M-token context window doesn't need it; volume is already bounded by RecallService's own budget (`maxItems`/`tokenBudget`) plus the `channelContext.promptRecentCount` history cap. The direct-OpenAI path (`ChatService.chat`'s fallthrough, used when the sidecar is disabled/unhealthy or for non-channel-voice personalities) INTENTIONALLY keeps `_buildGroupSystemPrompt`'s `promptMaxTokens` trim, since it's the unhappy-path fallback on a smaller-window, cost-sensitive model.

**Sandbox isolation:** Kata Containers, specifically `runtimeClassName: kata-qemu-runtime-rs` (Kata's Rust runtime — statically linked, no glibc coupling). Each `run_in_sandbox` call lands in its own tiny QEMU/KVM guest. Originally specified for gVisor, swapped to Kata on 2026-04-29 because Harvester's immutable SLE Micro host OS makes installing `runsc` impractical, and KubeVirt-on-bare-metal is already the platform's native model. Sandbox pods carry `dynatrace.com/inject: "false"` to keep OneAgent out of ephemeral guests (otherwise PID 1 doesn't release on container exit, ballooning wall-clock per execution to ~120s). See `k8s/sandbox/README.md` for the full Kata install play-by-play including the RKE2 containerd-template patch, the `kvm_amd sev=0` workaround for AMD hosts, and the smoke-test recipe. Cold start adds ~1.5–3s per call (VM boot); the agent prompt is aware of this so the model doesn't think the call hung.

**Toggle:** `AGENT_ENABLED=false` reverts channel-voice to direct OpenAI immediately. The `AgentClient` health-polls every 5s and considers the sidecar unhealthy after 30s without a successful Health response, falling through to direct OpenAI when the sidecar is gone.

**Health means "Chat works", not "the port is open" (`server.py` `ChatCircuitBreaker`):** `Health` used to be a hardcoded `healthy=True`, and the bot's `AgentClient` treats that RPC as its ONLY circuit breaker for the agent path — so the breaker's entire input was whether the gRPC server accepted a connection. That stays true while Vertex/GEAP credentials are revoked or Mongo is unreachable, and every channel-voice turn was then routed into a call guaranteed to fail (up to the 600s `chatDeadlineMs` each when the failure hangs rather than erroring). `Health` now reports a **consecutive-failure breaker over observed `Chat` outcomes** — no I/O in the health path, it only reads state `Chat` recorded. `AGENT_HEALTH_FAILURE_THRESHOLD` (default 3) consecutive failures trip it; any successful `Chat` closes it. **The half-open is load-bearing:** while unhealthy the bot STOPS sending `Chat`, so no success can arrive on its own and a naive breaker would latch unhealthy until a pod restart; after `AGENT_HEALTH_COOLDOWN_SECONDS` (default 60) the breaker reports healthy again to admit a trial `Chat`, and a failed trial re-opens it immediately and restarts the cooldown. Failures counted include every `Chat` exception, the not-configured case, and a turn that returns empty text (the bot already treats an empty turn as failed) — over-counting fails toward the safe direction (falling back to direct OpenAI). Do NOT "fix" health with `healthy = self._agent is not None`: `serve()` builds the agent before `server.start()` with no try/except, so that expression is a tautology in production. **A cancelled `Chat` counts too, and this is subtle enough to be worth stating: `asyncio.CancelledError` inherits from `BaseException`, so an `except Exception` in the handler never sees it — and a client-deadline expiry is delivered to a grpc.aio handler as exactly that.** Without the explicit `except asyncio.CancelledError` in `AgentServicer.Chat`, the most expensive failure mode of all (a backend that accepts the connection and goes silent, burning the bot's full 600s `chatDeadlineMs` on every message) recorded nothing and the breaker never opened. The handler additionally bounds its own turn with `AGENT_CHAT_TIMEOUT_SECONDS` (default 540, deliberately under the bot's 600s deadline) so the sidecar gives up first and the bot gets a real `DEADLINE_EXCEEDED` naming the bound.

**Degradation is announced, never silent:** three paths can hand the user something other than a normal agent reply, and each now says which. (1) Agent RPC failure → `ChatService.chat` falls through to direct OpenAI and attaches `result.fallback` naming the substitute model; the log line names it too. (2) `fallback_occurred` on `ChatResponse` is real plumbing now — the sidecar sets it when a turn ran on the generic `base.txt` instead of the bot's learned channel-voice `system_prompt`. (3) `buildTurnContext` throwing no longer silently strips personality + memory + history: the turn still runs (degraded-but-working is correct) but it is logged at error with the stack and flagged to the user. `bot.js` renders `result.fallback.notice` supplied by ChatService — it used to hardcode "Local LLM unavailable" for every fallback, mislabelling agent failures as a problem in an unrelated feature.

**K8s API timeouts (`k8s_client.py`) — two mechanisms, and the difference matters:** an API server that accepts the connection and goes silent parks the `asyncio.to_thread` worker forever AND holds the orchestrator's `ConcurrencyGate` permit. Permits are global and finite, and every K8s call in the sidecar runs on the default executor (`min(32, cpu+4)` workers), so repeated hangs walked the sandbox to a standstill only a restart cleared.

1. **REST calls** carry an explicit `_request_timeout` (default `(5, 30)`), which works as advertised.
2. **The exec/attach websocket IGNORES `_request_timeout`.** `ws_client.websocket_call` only applies it via `run_forever`, which is reached only when `_preload_content` is true — and we pass `False` (we need the live `WSClient` to write stdin). The hang is inside the `WSClient` constructor: `create_websocket` → `WebSocket.connect()` → `_http._open_socket` does `sock.settimeout(None)`, so connect/TLS/handshake are unbounded blocking reads. Verified empirically against a socket that accepts and never answers: `websocket.setdefaulttimeout()` does NOT fix it (`getdefaulttimeout()` is only read by `create_connection`/`WebSocketApp`), neither does `socket.setdefaulttimeout()` (defeated by the explicit `settimeout(None)`), and there is no seam to pass `sockopt`. What works is `_install_ws_connect_timeout` in `k8s_client.py`: it substitutes `kubernetes.stream.ws_client.WebSocket` with a subclass that defaults the documented `connect(timeout=…)` option. **This is a monkeypatch of a third-party symbol** — if a kubernetes upgrade stops resolving `WebSocket` through that module it silently stops applying, so it returns a bool, logs loudly on failure, and `tests/test_k8s_client_timeouts.py` pins it against a real silent socket.

`SandboxOrchestrator.run` bounds one execution (`overall_deadline_s`, default `wall_clock + 120`) inside the gate, returning `orchestrator_error="orchestrator_timeout"`, **plus** a separate `cleanup_deadline_s` (default 30s) on the `delete_job` in `_do_run`'s `finally`: `asyncio.wait_for` cancels the task and then waits for that `finally` before raising, so without its own bound a slow cleanup extends the permit hold past the deadline. An abandoned Job cleans itself up via `activeDeadlineSeconds` + `ttlSecondsAfterFinished`. Note the orchestrator deadline releases the *permit*, not the *thread*: `asyncio.to_thread` futures cannot be cancelled, so unwinding the worker thread is the job of the request-level bounds above — which is exactly why the websocket one had to be made real rather than assumed.

**Transient 503 handling:** the Gemini-native path attaches SDK-level exponential backoff (`agent.py` `_gemini_retry_options`: 4 attempts, 0.5→8s, jitter, on `429/500/502/503/504`). New models (e.g. `gemini-3.5-flash` at launch) spike 503 "model overloaded" errors; without this each one immediately fell through to the bot's direct-OpenAI fallback (`OPENAI_MODEL`, now `gpt-6-luna`), silently swapping the model. Retry is at the HTTP-call layer, NOT the agent turn, so sandbox tools are never re-executed. The bot's `AgentClient` chat deadline (600s) comfortably exceeds the ~8s retry budget.

**Gemini backend — Enterprise Agent Platform, NOT the consumer API (since 2026-08-05):** the sidecar's Gemini calls run on the Gemini Enterprise Agent Platform (GEAP, the rebranded Vertex AI, `aiplatform.googleapis.com`), not the consumer AI-Studio endpoint. This moves the `BLOCK_NONE` dual-use security workload onto the enterprise-governed surface (consumer AI-Studio runs Prohibited-Use abuse monitoring even on paid tier — a policy-suspension risk). Wired via env on `agent-deployment.yaml`: `GOOGLE_GENAI_USE_VERTEXAI=true`, `GOOGLE_CLOUD_PROJECT=revenant-discord-bot-2`, **`GOOGLE_CLOUD_LOCATION=global`** (the Gemini flash models 404 at `us-central1` on this project — they serve from `global`), `GOOGLE_APPLICATION_CREDENTIALS=/var/secrets/genai/key.json`. ADC comes from SA `agent-genai@revenant-discord-bot-2` (`roles/aiplatform.user`) mounted via the `agent-genai-sa` Secret; `GEMINI_API_KEY` is blanked in the sidecar env so the SDK can't pick the consumer backend. `active_genai_backend()` logs `genai_backend=enterprise` at startup. **ImagenService/LyriaService (the bot, not the sidecar) still use the consumer `GEMINI_API_KEY`** — only the sidecar moved. `mcp` is on 2.x (migrated 2026-09-26: the bearer header rides an `httpx2.AsyncClient` passed to `streamable_http_client`, and results use the 2.x `is_error`/`structured_content` names — the 1.x names silently read `None` under 2.x, swallowing tool errors). `tests/test_mcp_v2_compat.py` runs the real transport + client session against an in-process MCP server so an SDK break fails a test instead of `/obs dql` in prod. Production agent model: `gemini-3.8-flash` (sandbox-config `AGENT_MODEL`).

**Sandbox disposition — answer-directly-by-default (since 2026-08-06):** `TOOL_AVAILABILITY_PREAMBLE` in `agent.py` treats the sandbox as a LAST resort — the model answers most asks directly (instant) and only invokes `run_in_sandbox` when a correct answer genuinely requires execution (real network/recon, computing over data it can't derive, observing real runtime behavior). This was a latency fix: the old preamble pushed "when in doubt, run it," which fired a pod for ~46% of direct questions. Tune/verify with the offline eval harness (`agent-sidecar/eval/`, see its README) — it runs the real agent against a fake orchestrator and scores false-invocation / false-omission. The `Chat` handler emits `sandbox.invoked` / `sandbox.call_count` on an `agent.chat` span for Dynatrace to track the production invocation rate. Follow-up if prompt tuning proves insufficient: a pre-flight router/classifier.

**Web search on the text agent (since 2026-09-28, `agent.py`):** ADK's native `google_search` built-in is attached to `Agent.tools` alongside `run_in_sandbox` when `agent_web_search_enabled` (env `AGENT_WEB_SEARCH_ENABLED`, default `true`) AND the built model is a native `Gemini` instance whose name passes ADK's own `is_gemini_model()` (`_web_search_attached`) — LiteLlm-backed models never get it, and a `Gemini(...)` pointed at a non-`gemini-*` endpoint id is excluded because `GoogleSearchTool` raises "not supported" for it, which would fail every turn. **Never `GoogleSearchTool(bypass_multi_tools_limit=True)`** — that bypass mode crashes in ADK 2.10 with a `PydanticSerializationError` (`MockValSer`); the plain `google_search` instance works natively alongside a function tool in the same turn. `TOOL_AVAILABILITY_PREAMBLE` gets `WEB_SEARCH_PREAMBLE` appended only on turns where search is actually attached: for current/external facts (news, patch notes, what a website says, anything past training data) use `google_search`, never `run_in_sandbox` to scrape web pages or query search engines for information — the sandbox stays correct when the live network behavior of a specific target is itself the subject (an HTTP response's status/headers/TLS/redirects/timing, the raw content of a URL the user named, host recon). This split is deliberate: an earlier draft said "never fetch web pages in the sandbox" flatly, which contradicted the sandbox preamble's legitimate recon use. Observability: `web_search_queries` (sum of `grounding_metadata.web_search_queries` across the turn's events) is plumbed through `AgentChatResult` and recorded as `web_search.queries` on the `agent.chat` span, with one INFO log line when it's nonzero.

**Sidecar:** single-replica `Recreate` Deployment — concurrency state is in-process; **do not scale**.

**Tunables (sandbox-config ConfigMap):** `SANDBOX_INLINE_OUTPUT_CHARS`, `SANDBOX_WALL_CLOCK_SECONDS`, `SANDBOX_PER_USER_CONCURRENCY`, `SANDBOX_GLOBAL_CONCURRENCY`, `SANDBOX_MEMORY_LIMIT`, `SANDBOX_CPU_LIMIT`, `SANDBOX_BASE_IMAGE`, `SANDBOX_TRACE_RETENTION_PER_USER`, `SANDBOX_AGENT_TURN_CALL_BUDGET`. Health-breaker knobs (sidecar env, defaults are sane): `AGENT_HEALTH_FAILURE_THRESHOLD` (3), `AGENT_HEALTH_COOLDOWN_SECONDS` (60), `AGENT_CHAT_TIMEOUT_SECONDS` (540 — must stay under the bot's 600s `chatDeadlineMs`).

**Reaction reveal:** on a bot reply that ran code, react with 🔍 (source code), 📜 (stdout + stderr if non-empty), or 🐛 (stderr only) to get the artifact attached.

**Trace storage:** MongoDB `sandbox_executions` (one doc per call). The retention loop in the sidecar demotes >N (default 50) traces per user — older docs keep `exit_code`/`stdout`/`stderr`/`duration_ms` but null out `code`, `stdin`, `env_keys`, `egress_events`, `runtime_events`, `agent_rationale`. The `runtime_events` field is empty by default under Kata (no built-in syscall-deny telemetry); the field is reserved for future `auditd`-in-guest signals.

**Manifests:** `k8s/sandbox/` (tracked) — see its README for the kata-deploy prereq, apply order, and the two small edits the bot Deployment + NetworkPolicy need.

## Star Citizen Knowledge (sc-knowledge)

Spec: `docs/superpowers/specs/2026-09-26-star-citizen-knowledge-design.md`. A third, NEW Python service (`sc-knowledge`, `python:3.14-slim`, FastMCP, stateless streamable HTTP at `:8080/mcp` + `GET /healthz`) that both the agent sidecar and the voice sidecar attach to as an MCP toolset, so channel-voice chat and voice sessions can answer Star Citizen questions with live game data instead of stale parametric knowledge.

**Seven game-data tools** (plus the two member-hangar tools `sc_member_hangar` / `sc_member_fit_check`, see "Member hangar" below)**:** `sc_find_item` (items/components via the Star Citizen Wiki API with embedded UEX shop prices; SHIPS/VEHICLES resolve via UEX `vehicles` + `vehicles_purchases_prices` — e.g. "where can I buy a Scorpius" → New Deal, Lorville), `sc_compare_components` (shield/power_plant/cooler/quantum_drive/radar/weapon/missile, stat paths verified against live data, lower-is-better stats sort ascending; `purchasable_only=True` keeps only items with a current UEX shop buy price), `sc_faction_missions` (rank ladder + missions ranked by rep/min, outliers >3× median flagged with a caveat rather than silently trusted), `sc_trade_routes` (commodity/terminal-first resolution, profit capped by cargo SCU + budget aUEC, a Pyro `lawless` flag), `sc_commodity_prices`, `sc_location_shops` (what's sold at a place, and what's unique to it), and `sc_org_guides` (BM25 section search over the org's own curated guides).

**`sc_location_shops(location, category=None, exclusive_only=False, limit=40)` (added 2026-09-28):** answers "what's sold at Levski" / "what's unique to Levski for purchasing" — the gap the incident below fell into. Built from UEX `items_prices_all` (~24k price rows) + `terminals` + `categories`, no Wiki call. **Location resolution is exact-field-match-first, then token-match, most-specific tier first** (city/station/outpost → moon/planet/orbit → system → terminal name/nickname), so "Nyx" resolves to the star *system* rather than sweeping in the unrelated "Nyx Gateway" stations that merely token-match at the station tier, and "Levski" (a city) never pulls in the rest of Nyx. Only terminals with `is_available_live == 1` count for both resolution and exclusivity — UEX still carries dead rows like the pre-Nyx "Dumper's Depot - Levski". **Exclusive** means no other *live* UEX-reporting terminal has a buy price for that item — exclusivity is relative to player-reported UEX data, not ground truth, and the response says so. `category` accepts a raw section/category name or the `"ship parts"`/`"ship components"` and `"fps gear"`/`"fps equipment"` aliases (joinable with "or"); an unrecognised category is ignored with a note, never a failure. A broad query (e.g. a whole system) is capped: items are selected **round-robin across sections** (never section-sorted truncation, which starved a Levski "ship parts or fps" query down to just Armor and Clothing) up to `limit` (clamp 1–100), with `section_counts` carrying the untruncated per-section totals so the model can say what else exists there. **Latency:** all three datasets are prefetched at server startup (`warm()`) and cached with a 3600s TTL; past expiry a call is served the stale value immediately while a single-flight background refresh runs, so a cold post-restart call never pays the ~6 MB `items_prices_all` refetch inside the voice path's 6s tool bound.

**Sources — and why NOT p4k/datap4k/erkul:** UEX (`api.uexcorp.uk/2.0`) for prices/trade/vehicles, the Star Citizen Wiki API (`api.star-citizen.wiki/api`) for item/vehicle/mission/faction data, and the org's own curated guides for org-specific procedure knowledge. Unpacking the game's `.p4k`/`datap4k` archives or scraping erkul.games was deliberately avoided — both require either bundling extracted game assets (a licensing and staleness liability) or a scraper that breaks on every patch; UEX + the Wiki API are maintained, versioned, patch-aware public APIs that already do that work.

**Org guides — privacy is load-bearing, not incidental:** the org's curated guides are PRIVATE PDFs kept in repo-root `OrgGuides/` (git- and docker-ignored — this repo and its images are PUBLIC). They are converted to text and synced into a Kubernetes ConfigMap (`sc-org-guides`) by `scripts/sync-org-guides.sh` (pdftotext, 900 KB guard, `kubectl apply --server-side` — a client-side apply copies the whole ConfigMap into the 256 KiB-capped last-applied annotation and fails far below the guard), mounted read-only at `/guides` (`SC_GUIDES_DIR`) on sc-knowledge, and hot-reloaded on mtime change within 60s — adding or updating a guide is "drop a PDF, rerun the script," no redeploy. Guide text is never committed to git, never baked into an image, and never allowed into this documentation: refer to guide content only generically (as here), never by title or excerpt.

**Flags and secrets (both sidecars):** `SC_KNOWLEDGE_ENABLED` (default `false`) and `SC_KNOWLEDGE_URL` (default the in-cluster sc-knowledge Service) gate attachment on the agent sidecar and the voice sidecar independently — each is reversible on its own. `UEXCORP_BEARER` (optional, raises UEX rate limits) lives in Secret `sc-knowledge-secrets`, sourced from the repo's own `.env`, never committed.

**Cache TTLs + stale-on-error:** trade routes / commodity prices 1800s, item/vehicle prices 7200s, stats/missions/factions 43200s, name index/vehicles/terminals 21600s — chosen per how fast each upstream actually changes (prices drift hourly, stat blocks only move on a patch). On an upstream failure, a cached-but-expired value is still returned with `stale: true` + `age_minutes` rather than surfacing an error, because a slightly-stale trade route beats no answer in a voice conversation. (Exception: `sc_location_shops` also serves its expired price copy while a background refresh runs, so the first call after each hourly expiry reports `stale: true` with `age_minutes` ≈60 even when UEX is healthy.) Every result also carries `source` and `game_version` (except `sc_location_shops`, whose UEX price rows have no game version — it reports `latest_report` instead, so `note_patch` never fires for it) so a stale or off-patch answer is visible to the caller, not silently wrong.

**Isolation guarantee — probe-gated, never fails Chat:** the agent sidecar's `ScToolsProvider` builds the MCP toolset ONCE at startup, then gates *attachment per turn* on a cached availability check (30s cache): a `/healthz` probe (2s timeout) AND a real `get_tools()` on the toolset that must list at least one `sc_*` tool (5s bound; any exception/timeout/empty listing → unavailable). `/healthz` alone is not enough — an MCP-path-only failure (e.g. the 421 below) leaves it green while every tool silently fails to load under a preamble promising them. sc-knowledge being down degrades a turn to `SC_TOOLS_UNAVAILABLE_NOTE` (no tools, model still answers) rather than failing the whole `Chat` RPC or tripping the agent health breaker documented above. The toolset itself is a **non-closing proxy**: ADK's `Runner.close()` would otherwise close the shared MCP toolset after every single turn (it's built once, per-turn `Runner`s don't own it), so a wrapper intercepts `close()` as a no-op and the real toolset is only closed at process shutdown. Voice mirrors this with its own `ScToolExecutor`, opening a fresh MCP session per tool call (bounded, see below) rather than holding one shared session across a whole Live conversation.

**`/mcp` Host allow-list — or every in-cluster call is `421`:** mcp 2.2's `streamable_http_app` defaults `host="127.0.0.1"`, which silently enables DNS-rebinding protection with a loopback-only Host allow-list, so every in-cluster request (Host `sc-knowledge.discord-article-bot.svc.cluster.local:8080`) was rejected `421 Invalid Host header` while `/healthz` (a custom route, not guarded) stayed green. `server.py` passes explicit `TransportSecuritySettings` (protection ON) with `SC_ALLOWED_HOSTS` (comma-separated, `name:*` = any port; defaults to every in-cluster spelling of the Service plus loopback). A renamed Service or a new caller hostname must be added there. A 421 is a server-config problem, not the NetworkPolicy — the voice sidecar's startup warning prints the actual exception class/message for exactly that reason.

**`/healthz` never touches upstream:** it reports the CACHED live game version (`TTLCache.peek`, `null` when cold) and, if missing/expired, starts ONE single-flight background refresh. It used to await the UEX fetch (3 attempts × 8s read) — a UEX outage blew the kubelet's 1s probe timeout and restart-looped the pod; the tracked probes now also set `timeoutSeconds: 2`. The per-tool-call `note_patch` lookup is likewise bounded at 0.5s (under `asyncio.shield`, so the wait is abandoned, not the fetch) so a Wiki-only answer never waits on UEX and the voice 6s bound holds. `TTLCache` additionally backs off a failed key for 30s — during the window it serves the stale entry (or re-raises) immediately instead of paying the retry budget again.

**MCP timeouts — 3s / 15s, not the library defaults:** the `mcp_registry` profile for this toolset (`channel_voice`, auth-less) sets per-server `timeout=3` and `sse_read_timeout=15`. A hung sc-knowledge call inside a live voice or chat turn is worse than a fast, honest failure — 3s is enough for a normal MCP round trip against an in-cluster service, and 15s bounds how long a streaming response can be read before the caller gives up, so one bad upstream call can't stall a turn indefinitely.

**Sandbox avoidance — three independent layers, because any one alone is fixable but fragile:**
1. **Pre-computed tool results.** The agent's system prompt and the `sc_*` tool results themselves are the intended path to SC data — the model is never told "go fetch this yourself."
2. **A host-side backstop in `RunInSandboxTool`:** code/stdin matching `SC_DATA_HOST_PATTERN` (`uexcorp.space|uexcorp.uk|star-citizen.wiki|sc-trade.tools|scunpacked|starcitizen.tools|erkul.games|cstone.space|sc-craft.tools|robertsspaceindustries.com|spviewer.eu|scmdb.net` — the last six widened 2026-09-28 after the model was caught scraping those community sites through the sandbox for questions no `sc_*` tool covered) is refused BEFORE the concurrency budget or orchestrator are touched, returning `exit_code -4` / `use_sc_tools` — no pod is ever spawned for it, and the refusal still counts toward attempt telemetry so a model that keeps trying is visible. The refusal message now points at `sc_location_shops` and `google_search` (see "Web search on the text agent" above), not just the original five tools.
3. **A hard eval gate.** `eval/eval_sc.py` fails the suite if `sandbox_attempts_total` is ever nonzero for an SC-answerable prompt, and the production DQL check `fetch spans | filter span.name == "agent.chat" and toLong(sc.tool.calls) > 0 and sandbox.invoked == true` should read ~0 — a model routing SC questions through the sandbox instead of the tools is a regression this DQL line is meant to catch immediately, not eventually.

**2026-09-28 hallucination incident and fix:** trace `d912da65f299ceea9a78c4d413058069` asked "are there any ship parts or fps equipment that are unique to Levski" — SC tools were attached, but none of the original six covered "what's sold at this place," so the model made one `run_in_sandbox` call whose code was only a comment (`# Let us check what UEX or star citizen tools have for Levski`) and then answered from stale training memory ("Levski vaulted in 3.12" — false; Levski has 22 live UEX terminals with 77 exclusive items). Root cause was two gaps, both closed the same day: no tool answered location-inventory questions (fixed by `sc_location_shops` above), and the text agent had no web-search fallback for genuinely uncovered SC questions, so its prompt's "use web search" instruction had nothing behind it (fixed by native `google_search`, see "Web search on the text agent" above). Every SC-facing prompt (`sc_tools_preamble`, `sc_tools_unavailable_note`, and this section's voice note) now also states outright: the model's Star Citizen training knowledge is years out of date, and it must never assert from memory that something is vaulted, removed, not in the game, or located somewhere — tool and search results beat memory when they disagree.

**Rank/mission outlier flagging:** `sc_faction_missions` ranks by rep-per-minute, but a single anomalous record (e.g. one very-high-rep mission that isn't representative of the grind) can otherwise dominate the ranking and mislead a player. Missions more than 3× the median rep/min are kept in the results but flagged with a caveat rather than dropped — visible-but-distrusted beats silently-hidden or silently-trusted.

**Vehicle ambiguity — token filter, not fuzzy-match-everything:** `sc_find_item` only surfaces a ship/vehicle as an ambiguity candidate when it shares a *whole token* with the query (not a fuzzy/substring match), and otherwise returns an honest `not_found` rather than guessing. Loose fuzzy matching on vehicle names pulled in unrelated noise (e.g. a query for one ship fuzzy-matching a completely different one that merely shares a few letters); an honest "not found" is more useful than a wrong guess in a voice conversation where the user can't see a disambiguation list.

**Voice tool-call plumbing:** the voice sidecar's `ScToolExecutor` reads each tool's MCP 2.x `input_schema` at startup and sanitises it (`_sanitize_schema` drops `title`/`default`/`$schema`/`additionalProperties` and collapses `anyOf`-with-null) before handing it to Gemini Live as a `FunctionDeclaration` — Live's documented schema subset is stricter than raw MCP JSON Schema, so sanitising is a defensive measure — whether Live actually rejects (or silently drops) a raw MCP schema has NOT been verified; the sanitiser exists so we never have to find out mid-conversation. Each call is bounded to **6s total, including opening the fresh MCP session**, runs as a task off the audio pump (never blocking it), and is cancelled both on an explicit `tool_call_cancellation` and when the pump itself exits — a cancelled or late result is dropped, never replayed into a session it no longer belongs to, and never sent to any session but the CURRENT one (a stale response landing in a resumed/new session would look like an answer to a question that was never asked in it). If a Live session fails to open WITH SC declarations attached, the sidecar makes one immediate search-only retry and the conversation stays search-only for its duration (counted as `sc_fallbacks` in the session END log) rather than looping on a broken attach.

**Disputed game mechanics — search, then defer; never argue from memory (both surfaces, since 2026-09-29):** in a voice session a player described NAV-mode quantum-drive behaviour they were seeing live ("engines max at 205; spool the quantum drive to 100% and I can go 1,000 m/s") and the model argued ~10 turns from stale memory ("probably your afterburner", "my data says otherwise"), even after "recheck your sources" — with `tool_calls=0`, since no `sc_*` tool covers flight mechanics. One rule now rides on both surfaces: voice `SC_VOICE_NOTE` (`voice-sidecar/src/live_bridge.py`) and the text agent's `_sc_dispute_rule` inside `sc_tools_preamble` / `sc_tools_unavailable_note` (`agent-sidecar/src/agent.py`). Search variant (voice always; text when `google_search` is attached): look mechanics up with search rather than memory, look it up again when a player disputes a claim or describes what they see in-game right now, and if still unconfirmed defer to the player's live observation. The re-check names whichever sources are actually attached: "sc_* tool or google_search" / "tool or search" when the `sc_*` tools are on (so a dispute about something a tool covers re-calls the tool rather than only searching), plain "search again" in the text agent's sc-unavailable note (`_sc_dispute_rule(tools_attached=False)`, which also drops the "anything the sc_* tools don't cover" scope) and in voice's standalone note. No-search variant (`SC_TOOLS_PREAMBLE` / `SC_TOOLS_UNAVAILABLE_NOTE`): don't repeat the claim from memory — say it can't be verified live and defer. **Voice: exactly once in every session.** `SC_VOICE_NOTE` is only appended when SC declarations are attached, so when they are NOT (sc-knowledge off/unavailable, empty declarations, or the search-only connect fallback) `_live_config` appends the standalone `SC_MECHANICS_VOICE_NOTE` instead — same rule (Google Search is always attached in Live, so the search variant always applies), names no `sc_*` tool. Exactly one of the two is appended per config, never both; the dispute sentence's tail is the shared constant `SC_DISPUTE_TAIL`, and `tests/test_live_bridge_mechanics_note.py` counts it to pin exactly-once across SC-attached, SC-absent and fallback. Consequence: the voice `system_instruction` is never just the bare persona any more, even with SC and control tools both off (an empty persona is dropped before joining, so there is no leading blank line). Eval: `sc_eval_set.py` carries an `sc_dispute` case that replays the incident's exchange via per-case `history` (see `agent-sidecar/eval/README.md`); it is scored like `uncovered_sc` with the soft `NO WEB SEARCH in N/M runs` flag, no new gate.

**Sandbox/voice declaration reload:** SC tool declarations are loaded once at startup on the voice sidecar; a newly added/changed sc-knowledge tool needs a sidecar restart to be picked up (this is a known, accepted limitation, not a bug).

**Adding SC Trade Tools (or another future SC MCP server) later:** the `mcp_registry` is a per-profile registry keyed by name (`channel_voice` is sc-knowledge's entry today) — a second server is added as its own registry entry with its own `token_attr` for auth, alongside sc-knowledge rather than folding into it. No code change to `ScToolsProvider`/`ScToolExecutor` should be needed beyond registering the new entry.

**Deploy rules (same posture as the sandbox/voice sidecars above):** apply only from the deployed overlay (`k8s/overlays/deployed/sc-knowledge-{deployment,service,networkpolicy}.yaml`), never the tracked `k8s/sc-knowledge/` placeholders; `RollingUpdate` (sc-knowledge is stateless, unlike the agent sidecar); image tagged with the git short SHA, never `:latest`; NetworkPolicy egress rules added on BOTH the agent and voice sidecars for sc-knowledge port 8080, and sc-knowledge's own NetworkPolicy only accepts ingress from those two sidecars. Rollout order was sc-knowledge first, then flip `SC_KNOWLEDGE_ENABLED=true` on the agent sidecar (verify via text chat + the `sc.tool.calls`/sandbox DQL check above) and only then on the voice sidecar (verify via `scripts/smoke-voice-sc.js`) — each flag is independently reversible if its half regresses.

### Member hangar (per-member ship loadouts, since 2026-10-09)

Spec: `docs/superpowers/specs/2026-10-09-member-hangar-design.md` (project 1 of 3). Each member's Star Citizen ships and what is fitted in them, answered by tool in text AND voice: "what's a purchasable upgraded shield for my Harbinger?" (UC1), "I just looted a Hemera quantum drive, is it a usable upgrade for any of my ships?" (UC2), "I can't use this Hemera, can Micro?" (UC2b), "what's on my Connie?" (UC4).

**Service — `hangar-service/` on Cloud Run, NOT in the cluster:** FastAPI + Firestore (Native, `us-central1`) in GCP project `revenant-discord-bot-2`, region `us-central1`, image in Artifact Registry `us-central1-docker.pkg.dev/revenant-discord-bot-2/revenant/hangar-service:<git-short-sha>` (never `:latest`), runtime SA `hangar-runtime@` (`roles/datastore.user`). **min-instances 1** (~$7/month): a cold Python/Firestore start plus the Wiki vehicle-index warm-up exceeds voice's 6s tool bound and Discord's 3s autocomplete deadline. Catalog data is cached 12h stale-while-revalidate, warmed at startup; Cloud Run runs request-only CPU, so a background refresh may finish on a later request (accepted). Deploy commands, env and API: `hangar-service/README.md`.

**Auth — the app is the only gate, and the audience must match byte for byte:**
- **Cloud Run invoker IAM check is OFF (`--no-invoker-iam-check`, since the web editor).** The org's domain-restricted-sharing policy (`iam.allowedPolicyMemberDomains`) blocks an `allUsers` invoker, so `--allow-unauthenticated` fails — and browsers coming through the load balancer can't present a Google invoker token at all. So this ONE service (the org policy is untouched) skips Cloud Run's invoker check and **the app's own authentication is the only gate**: Google ID tokens for the bot and sc-knowledge (unchanged — same `run.app` URL, same exact audience), Discord session cookies for browsers. Every `/v1` and `/api/v1` route stays authenticated; only `/health`, `/version.txt` and the static editor files are open, and none carries member data. The old `roles/run.invoker` binding for `hangar-api@` is still there (harmless; needed again if the check is ever re-enabled). Do NOT "fix" an open `/health` by re-enabling the check — it would lock every browser out. Unauthenticated surface (none of it returns member data): `/health`, `/healthz`, `/version.txt`, the static editor, and the login routes `/api/auth/login|callback|logout` plus `/api/me` (401 without a session). The two `run.app` URLs are exactly as public as `hangar.aklabs.io` — never rely on the load balancer for access control (the `__Host-` cookie isn't sent there and session writes require `HANGAR_PUBLIC_ORIGIN`, so this is safe today).
- **The app re-verifies** the Google-signed ID token (audience `HANGAR_AUDIENCE`, `email_verified`, email in `HANGAR_ALLOWED_CALLERS`) and enforces writes: `X-Acting-Member` must equal the path member or be in `HANGAR_ADMIN_IDS` (same ids as `BOT_ADMIN_USER_IDS`). Reads of any member are allowed (UC2b).
- Cloud Run serves two URLs — `https://hangar-service-hvmf2jpuca-uc.a.run.app` and `https://hangar-service-278098364045.us-central1.run.app`. **The audience is exactly `https://hangar-service-hvmf2jpuca-uc.a.run.app`** (no trailing slash); callers mint for, and call, that URL. Using the other form is a 401.
- **Health is `/health`, not `/healthz`:** Cloud Run's front end reserves paths ending in `z` (Google's own 404). `/healthz` stays for local parity. `/health` is open (invoker check off).

**Credentials in the cluster:** SA `hangar-api@` (no project roles; it only mints ID tokens for itself) — its JSON key lives ONLY in Secret `hangar-api-sa`, mounted read-only at `/var/secrets/hangar/key.json` in all four callers: the **bot** (`/hangar`), **sc-knowledge** (read tools), and the **agent** and **voice** sidecars (chat edits). All four run as uid 1000, which must be able to read the file (default secret mode 0644 works; `defaultMode: 0400` breaks it — the caller then answers `unavailable` with a WARNING naming the path). Callers' env: `HANGAR_API_URL` (= the audience URL above) and `HANGAR_SA_KEY_PATH` (default `/var/secrets/hangar/key.json`). Minting calls Google's token endpoint, so every caller pod — including the agent and voice sidecars — needs NetworkPolicy egress to `oauth2.googleapis.com` and `*.run.app` on 443. **Key rotation needs pod restarts** — every caller builds its credentials once and caches them. Both the agent and voice sidecars prewarm their ID token at startup (background, never raises), so the first edit doesn't pay for the mint.

**Data model:** Firestore `members/{discordId}/ships/{shipId}` = `{vehicleUuid, vehicleName, vehicleClassName, nickname, fitted: {<slot>: {itemUuid, itemName}}, createdAt, updatedAt, updatedBy}`. `fitted` holds ONLY changes from stock (fitting a slot's stock item clears it). A member may own several of one model; nicknames disambiguate. The **effective loadout** = stock slots with `fitted` applied, each `{slot, type, sizeMin, sizeMax, compatibleTypes, item, source: stock|fitted}`. Member ids must be numeric (1–32 digits).

**Catalog — from Star Citizen Wiki vehicle `ports[]`:** a port is a slot when its OWN `editable` is true and its type (or, empty in stock, a compatible type) is QuantumDrive, Shield, PowerPlant, Cooler, Radar, WeaponGun, Turret, MissileLauncher, WeaponMining or TractorBeam. **Nesting rule:** ports are walked at every depth and the parent's `editable_children` is NOT used — live data has S5 turret gimbals with `editable_children: false` while the gun inside is `editable: true`, so following the flag would hide every swappable turret gun. Slot ids join port names with `/` at whatever depth the port sits (no cap; e.g. three levels deep on the Taurus's manned upper turret: `hardpoint_turret_base_upper/hardpoint_weapon_left/hardpoint_class_2`). **Refitting a parent slot hides its stock children.** **Missiles are not tracked** (fit check answers `not_tracked`); racks are `editable: false` on the ships checked.

**Tools (sc-knowledge, so text and voice both get them):** `sc_member_hangar(member_id, ship=None)` (ship resolved within that member's hangar: exact nickname → nickname fuzzy → exact model → model token/prefix with a small shorthand table, "Connie" → Constellation → model fuzzy; ambiguous → candidates) and `sc_member_fit_check(member_id, item)` (per-slot `upgrade`/`downgrade`/`sidegrade` (≤2% on the key stat `sc_compare_components` ranks by)/`same`/`unknown`, plus `not_compatible` ships with `size_mismatch`/`no_slot`/`loadout_unavailable`). UC1 = `sc_member_hangar` + `sc_compare_components(purchasable_only=True)`. The sc-knowledge client is **read-only** (only `GET …/hangar`, never `X-Acting-Member`; a test pins it), token + request bounded at 3s, responses cached 30s, and each tool has a **5s overall deadline** under voice's 6s bound. A hangar outage returns `error("unavailable")`, never raises, never fails a turn. **`compatibleTypes` parity rule:** sc-knowledge's fit check applies the SAME compatibility rule as hangar-service's `check_compatible` (type in the slot's `compatibleTypes`, sub-types only when the slot lists some and the item's isn't `UNDEFINED`, size in range) using the `compatibleTypes` hangar-service puts on every loadout slot — change one, change both.

**Prompting — tool-called, never injected:** ship data is never put in the prompt. One sentence (`SC_HANGAR_RULE` in `agent-sidecar/src/agent.py`, both `web_search` variants; a short spoken version in voice `SC_VOICE_NOTE`) says: use the hangar tools only when the question is about a member's own ships or loadouts, never bring up anyone's ships unprompted, `member_id` is the numeric Discord ID from the `[Name · id]` labels or the "People in this conversation" roster, "my" = the labelled speaker. Voice has no per-turn id labels (Live audio) — the session opener is the roster's current speaker. **Voice limitation:** the roster is built once at session open, so a later speaker named only by a `[SPEAKER: name]` marker may not be in it — their "my" can't be resolved to a Discord ID, so the hangar tools can't be called for them (same mid-session-newcomer gap as the identity roster; nothing in the prompt handles it yet). The sc-unavailable note says hangars can't be looked up either (names no tool). `_SC_UNCOVERED` says "stock vehicle loadouts" with a pointer to the hangar tools, so the ordered fallback's step (2) never routes a member's own loadout question to google_search. Eval: four hangar cases in `agent-sidecar/eval/sc_eval_set.py` against the real service with fake members seeded by `eval/seed_hangar_eval.py --seed/--cleanup` (run in the sc-knowledge pod — the bot image has no Python), scored on the `member_id` argument, plus an `unprompted_hangar_calls` gate over every other case and a soft UC1 flag when no `sc_compare_components(purchasable_only=True)` follows the hangar call (see `agent-sidecar/eval/README.md`).

**Chat edits — text AND voice (project 3, since 2026-10-09).** Spec: `docs/superpowers/specs/2026-10-09-hangar-chat-edits-design.md`. Members record changes by saying what they DID — "I put the Hemera in my Connie", "I just bought a Cutlass Black", "I put my Harbinger's shields back to stock" — or by explicitly asking to update their OWN hangar ("put my Harbinger's shields back to stock", "mark my Connie as having a Hemera"), and the bot writes at once and says what changed ("Connie's quantum drive: Bolon → Hemera"). No pending-confirmation store.
- **Tools (same names/semantics on both surfaces):** `hangar_fit(ship, item, slot=None)` → `POST /v1/members/{id}/fit`; `hangar_add_ship(vehicle, nickname=None)` → `POST /v1/members/{id}/ships`; `hangar_reset(ship, slot)` → `POST /v1/members/{id}/ships/{shipRef}/reset` (`slot` required: a hint, or `"all"` for the whole ship — the model asks if the user didn't say). hangar-service does ALL resolution server side: ship text within the member's own hangar (same resolver as `sc_member_hangar`, `src/ship_resolve.py`, KEEP IN SYNC), item text by catalog (exact, then fuzzy — "hemera qd", "lorica shields"; responses carry the canonical `item.name` and `item.matchedBy: "exact"|"fuzzy"`), slot hints ("left", "nose", "2", "shields", "all"). Errors are the service envelope handed to the model verbatim: 409 `ambiguous` + `field` (`"ship"`|`"item"`) + `candidates`, 409 `choose_slot` + `slots`, 404 `not_found` (+ `owned` for a ship, `suggestions` for an item), 422 `incompatible` + `reason` (`size_mismatch`|`no_slot`), `forbidden`, `unavailable`, `invalid_request`. Endpoint details: `hangar-service/README.md` "Chat edits". Each tool: 5s (token mint + request), never raises, writes send `X-Acting-Member`.
- **Binding rule — the acting member is supplied by trusted plumbing, NEVER a tool argument.** No tool has a member parameter, so "put a Hemera in Micro's Titan" can only touch the speaker's own hangar (and the model is told to say chat edits only apply to your own hangar). **Text:** `ChatRequest.user_id` (the Discord ID the bot sends for the turn's author), bound into the per-turn tool instances (`agent-sidecar/src/hangar_edit.py` `HangarEditTools`, same pattern as `RunInSandboxTool(user_id=…)`). **Voice:** the current floor holder's Discord ID from `SetSpeaker.user_id`, tracked per session in the sidecar (`live_bridge._SpeakerIdentity` on `_SessionRef`, preserved across reconnects) and bound when the tool call ARRIVES (a speaker change while the write runs can't redirect it); before the first SetSpeaker, `SessionStart.user_id` (the opener). **The bot sends SetSpeaker on EVERY floor-holder change** — id-only (`{userId, displayName: ''}`) when the speaker's name hasn't resolved, then once more with the name when it does (`VoiceService._handleUserPcm`, `g.lastSpeakerNameSent`). The sidecar's identity follows `user_id` ALONE: a non-empty id sets it (an empty `display_name` just means no `[SPEAKER:]` marker); only an empty `user_id` (the Phase 4 floor-release clear) clears it, and then the opener fallback does not come back. Why both halves: grpc-js reports a failed write asynchronously, so the release's clear can be lost — previously a nameless next holder sent nothing and edits stayed bound to the PREVIOUS holder. Empty/non-numeric id → `{error: "unknown_speaker", message: "I can't tell who's speaking, so I can't edit a hangar right now — use text chat or the web editor."}` without calling the service. Admins get no cross-member chat edits — they use the web editor.
- **Prompt (one short sentence each):** agent `SC_HANGAR_EDIT_RULE` inside `sc_tools_preamble` / `sc_tools_unavailable_note` (both `web_search` variants, only on turns the tools are attached); voice `HANGAR_EDIT_NOTE`, appended exactly once per session whenever the declarations are attached, with or without the sc_* tools (beside `SC_VOICE_NOTE` or the standalone `SC_MECHANICS_VOICE_NOTE`). Rule: call the edit tools ONLY when the speaker says they DID something to their own ships or explicitly asks to update their own hangar; never for advice/hypothetical questions ("should I…", "would X be better…"); on `choose_slot`/`ambiguous` ask a short follow-up (voice: at most three options spoken); after a write state what changed using the canonical item name returned; after a `maybe_applied` result don't repeat the write (never `hangar_add_ship` again) — check with `sc_member_hangar` first (voice without sc_* tools: say it may have saved and to check); only the speaker's own hangar.
- **`maybe_applied` (timeouts after commit):** every tool is a write, so a timeout or cancellation AFTER the request went out can't tell whether it landed. The result is `{error: "unavailable", maybe_applied: true, message: "The hangar service didn't answer in time — the change may have been saved; check before retrying"}` — returned for a timeout after the request went out, ANY other failure once the request was handed to httpx except a connect error (RemoteProtocolError, ReadError, read/write timeouts, …), and a non-JSON 5xx (a gateway 502/504 from Cloud Run/the LB; a 5xx carrying the app's own `{error,…}` envelope passes through). A failure before anything was sent — token mint, connect — is a plain `unavailable`. Same rule on both sidecars. Voice: the 6s bridge bound returns it too; a call the model cancels can't be answered, so the sidecar logs it as `-> cancelled, maybe_applied`. A blind retry of `hangar_add_ship` would add a second ship — that's why the prompt forbids it.
- **Voice plumbing:** local Live tools like `end_conversation`/`go_quiet` — declared in the SAME `Tool(function_declarations=…)` (order: control, hangar, sc_*), answered in-sidecar (never the MCP executor; a `hangar_*` call with edits off is `unknown_tool`), run as a task off the audio pump with a 6s total bound (`HANGAR_CALL_TIMEOUT_S`), FunctionResponse sent to the CURRENT Live session only (a late result after a reconnect is dropped and logged — the write itself still happened). Connect fallback: they ride the control layer — kept when the sc_* declarations are dropped, dropped together with the control tools on the second step (also when control tools are off but edits are on).
- **Flags/credentials:** `HANGAR_API_URL` (exactly `https://hangar-service-hvmf2jpuca-uc.a.run.app`, also the token audience), `HANGAR_SA_KEY_PATH` (default `/var/secrets/hangar/key.json`, Secret `hangar-api-sa`), `HANGAR_EDITS_ENABLED` (default true when `HANGAR_API_URL` is set; can only turn edits off) — on the **agent** and **voice** sidecars. **On the text agent it does nothing unless `SC_KNOWLEDGE_ENABLED=true`:** the edit tools and their prompt sentence only attach on turns where an SC note is in play. Voice attaches them independently of sc-knowledge. `hangar-api@` is already an allowed caller.
- **Logs/telemetry (never truncated, never tokens):** agent: INFO `hangar edit: tool=… member=… args=… result=… changes=…` per call and `agent.chat` span attr `hangar.edits`; voice: INFO `voice: hangar edit <tool> id=… member=<id> ship=… item=… vehicle=… slot=… -> <ok|error code> (<ms>ms) [ship_label=…] [changes=[slot: from -> to; …]] [maybe_applied=True] [message=…]` per call (`-> cancelled, maybe_applied` for a cancelled call), `hangar_edits=N` appended LAST on the `voice: session END` line and `voice.hangar_edits` on the `voice.session` span. Both count only writes that changed something (no error, not `unchanged`). hangar-service logs `hangar: chat fit:` / `hangar: chat reset:` per changed slot.

**`/hangar` (bot, `commands/slash/HangarCommand.js` + `services/HangarClient.js`):** `list [member]`, `add ship [nickname] [member]` (catalog autocomplete), `rename ship nickname [member]`, `remove ship [member]` (both autocomplete from the target's hangar). Ephemeral, deferred before any call. `list` is open to everyone for any member (reads are allowed by design); edits are self-only unless the invoker is a bot admin — the bot refuses first and the service re-enforces via `X-Acting-Member`, which `HangarClient` always sets to the invoking user. `HangarClient` never throws (`{ok:false, error}`), one 5s deadline covers token mint + fetch. Outage → "Hangar service is unavailable right now." **Registered only when `HANGAR_API_URL` is set — including in the environment that runs `scripts/registerCommands.js`:** registration replaces the whole command set, so running it without `HANGAR_API_URL` silently DROPS `/hangar` (it logs a WARNING). Run it from the bot pod. Autocomplete for rename/remove can come back empty while the catalog is cold (a lighter endpoint is a possible follow-up). **`/hangar list` ends with "Edit in the browser: <url>"** when `HANGAR_EDITOR_URL` (`config.hangar.editorUrl`, production `https://hangar.aklabs.io`) is set — also on the empty-hangar reply; the footer's length is reserved before the "…and N more" truncation so the reply stays ≤ 2000 chars. Unset = no footer.

## Voice (discord-article-bot-voice sidecar)

When `VOICE_ENABLED=true`, `/voice join` puts the bot in a Discord voice channel and routes audio through a **second, separate** Python gRPC sidecar — `discord-article-bot-voice` — that hosts one Gemini Live session per active voice channel. It is a distinct Deployment from the agent sandbox sidecar (`discord-article-bot-agent`): they solve different problems and have opposite scaling needs.

**New-sidecar rationale (RollingUpdate/scalable vs. the agent sidecar's Recreate/do-not-scale):** the agent sidecar keeps sandbox-orchestration concurrency state in-process, so it must stay single-replica `Recreate` and never scale. The voice sidecar instead holds long-lived, real-time gRPC audio streams for as long as the bot sits in a voice channel — a `Recreate` rollout would drop every live call. It ships as its own `RollingUpdate`, horizontally scalable Deployment (`k8s/voice/voice-deployment.yaml`) for exactly that reason.

**Reuses `agent-genai-sa` (no new secrets):** the voice sidecar's Gemini Live calls run on the same GEAP/Vertex backend as the agent sidecar — `GOOGLE_GENAI_USE_VERTEXAI=true`, `GOOGLE_CLOUD_PROJECT=revenant-discord-bot-2`, **`GOOGLE_CLOUD_LOCATION=us-central1`** (NOT `global` like the agent sidecar — `gemini-3.8-live` serves only there on this project; see the Live-model paragraph under "Speaker Identity"), ADC via the `agent-genai-sa` Secret mounted at `/var/secrets/genai/key.json`, `GEMINI_API_KEY` blanked. `serviceAccountName: agent-sa` is reused too (`roles/aiplatform.user` is project-wide, so the region change needs no IAM change). Nothing new to provision in the cluster.

**`dynatrace.com/inject` — deliberately left enabled:** unlike the ephemeral Kata sandbox pods (which disable injection because PID 1 doesn't release cleanly, ballooning per-call wall clock), this is a long-lived, observability-first service — same posture as the agent sidecar's deployed manifest, which also does not set the annotation. Both OneAgent and the sidecar's own OTLP spans reach Dynatrace.

**Wake word (openWakeWord, keyless/offline, per-speaker):** audio is only forwarded to the Live model after openWakeWord detects the wake phrase locally (`VOICE_WAKE_WORD` label, default `"hey jarvis"`). No API key — the ONNX models run in-process via `onnxruntime-node`. This keeps ambient channel audio private and avoids streaming/billing on conversation the bot wasn't addressed in. The three-stage chain (melspectrogram → embedding → wake model) and its exact mel-frontend params (1280-sample frames, 5 mels/frame, 76-frame window at stride 8, `x/10+2` mel transform, int16-range float32 input) are ported from the `openwakeword_wasm` reference and vendored in `models/openwakeword/` (Apache-2.0). Four pretrained phrases: hey jarvis, alexa, hey mycroft, hey rhasspy. Tunables: `VOICE_WAKE_MODEL`, `VOICE_MEL_MODEL`, `VOICE_EMBEDDING_MODEL`, `VOICE_WAKE_THRESHOLD` (default 0.5). **Per-speaker gates:** one wake-gate set is built lazily per Discord `userId` (via `_perUser`), so each speaker in a multi-user channel has their own independent detection; the module-level ONNX session cache shares model weights across all speakers to avoid duplication. Note: `onnxruntime-node`'s `session.run` is async while the `WakeWordGate` contract is sync, so the engine runs the ONNX chain on an async queue and surfaces detections via a flag `process()` reads on the next call (sub-frame <80 ms lag).

**Voice Activity Detection (Silero VAD, per-speaker):** per-speaker neural VAD (Silero v5.1, `services/voice/SileroVad.js`, via `onnxruntime-node`) detects speech on 512-sample / 32 ms windows at 16 kHz, replacing the fixed mean-abs energy gate. One VAD instance runs per Discord `userId` (lazily created via `_perUser`), carrying its own stateful context tensor across chunks; the module-level ONNX session cache shares model weights across speakers. Endpointing is now a correct **Gemini Hybrid VAD**: once a turn opens, audio streams continuously (including trailing silence) so Gemini's server-side VAD sees real end-of-speech as a fallback; client-side `SileroVad.speechEnd` fires an early `audio_stream_end` that finalizes after `VOICE_SPEECH_END_SILENCE_MS`. Silero model vendored at `models/silero/silero_vad.onnx` (MIT). Tunables: `VOICE_VAD_THRESHOLD` (default 0.5), `VOICE_VAD_MIN_SPEECH_FRAMES` (2, ~64 ms), `VOICE_VAD_MIN_SILENCE_FRAMES` (24, ~768 ms), `VOICE_VAD_MODEL` (path).

**Session longevity — sliding-window context compression + resumption:** Audio-only Gemini Live sessions naturally cap at ~15 minutes because audio accrues ~25 tokens/s, and the Live context window fills. **Sliding-window context compression** removes this cap by storing a server-side resumption handle and compressing the session's context history once token count exceeds the trigger threshold. Trigger via `VOICE_CONTEXT_COMPRESSION_TRIGGER_TOKENS` (default 25000). **Session resumption** stores that handle and, on a dropped connection or a `GoAway` pre-disconnect warning from the server, transparently reconnects using it — the handle carries all conversation context, so re-seeding is not needed and no error surfaces to the bot. A failed (re)open itself (expired/consumed handle, a transient GEAP 503 spike) is retried with exponential backoff + jitter (0.5s → 4s cap) against the same reconnect budget rather than surfacing immediately as a fatal error. Resumption is capped at `VOICE_MAX_SESSION_RECONNECTS` (default 5) reconnection attempts total, covering both successful-session reconnects and failed-open retries; disable the feature entirely with `VOICE_SESSION_RESUMPTION_ENABLED=false`. **Note:** there is a mid-reconnect audio gap of ~1–3s (a full Live-session open) — frames arriving while no session is open are dropped, not buffered, because replaying stale audio after a resume would read as current speech; a dropped `audio_stream_end` (turn-finalize signal) is the one exception — it's replayed once immediately after the new session lands, since the bot won't resend it on its own. **Prerequisite to observe any of this:** `VoiceService._tick` force-ends the session at `VOICE_MAX_SESSION_SECONDS` (default 600s in `config/config.js`) regardless of resumption — at that default the ~15-min Live cap is never the binding constraint, so `VOICE_MAX_SESSION_SECONDS` must be raised for session longevity to matter in practice (it remains the cost guard; the default is intentionally left unchanged here).

**Turn rhythm:** wake → reply → "hot" follow-up window (`VOICE_FOLLOWUP_WINDOW_MS`, default raised to 60s in the deployed configmap; **each reply resets it**, so a back-and-forth needs no re-wake) → idle (`VOICE_IDLE_TIMEOUT_MS` tears the session down). `VOICE_MAX_SESSION_SECONDS` is a hard belt-and-suspenders cap independent of idle/follow-up timing.

**Active-speaker floor control:** in multi-user voice channels, the first speaker to wake the bot holds the floor (`FloorControl.js`); only the floor-holder's audio is forwarded to Gemini Live. When a second speaker talks, they are detected as "waiting" (`FloorControl.waiting()`), logged to observability, but their audio is withheld from the model — preventing crosstalk and keeping the conversation coherent. The floor is released when the session idles or ends. This design enables human-like deferral interactions in later phases: Phase 4 will lean on `FloorControl.waiting()` to craft replies that acknowledge waiting speakers ("let me finish with Alice, then I'll get to Bob").

**Per-speaker transcript attribution:** voice transcripts are authored with the floor-holder's real Discord `userId` (not the placeholder `'voice-user'`), so `/tldr` and centralized recall show who actually spoke — essential for multi-user channels.

**Pre-roll buffer:** while idle, `VoiceService` keeps a rolling ~3s pre-roll (`MAX_PREROLL_FRAMES`) of 16k PCM. On wake it captures that buffer (plus any audio arriving during the ~3s session-open startup) into `g.pending` and flushes it into the Live session right after `sendStart`, so a first-turn question spoken in the same breath as the wake phrase ("hey jarvis, what's 2+2") isn't lost in the wake→session gap. The wake-phrase audio is sent through too (harmless; reads as address). **`g.pending` is bounded** at `MAX_PENDING_FRAMES` (~10s) because an unbounded buffer would flush minutes of backlog into the model as if it were current speech — the same reason the reconnect path drops frames instead of buffering them. **It is bounded DROP-NEWEST, the opposite of the pre-roll, and the difference is load-bearing:** the pre-roll is a sliding window over unclaimed ambient audio (its oldest frame is the least interesting thing in it), while `g.pending` is one utterance captured from its start — its oldest frames are the wake phrase and the beginning of the question. Bounding it drop-oldest (as the first cut did, by analogy with the pre-roll) truncated the head: "hey jarvis, what's the population of Brazil compared to India?" reached the model as "…compared to India?" and it answered the wrong question. At 10s the eviction branch is out of reach for a normal open (~3s), but it IS reachable: the context build is bounded at `CONTEXT_BUILD_TIMEOUT_MS` (15s), so a hung `_contextBuilder` gives a 10s buffer up to 5s of overflow. That is the intended shape — when eviction happens the head survives, only the tail is lost, and the tail keeps arriving live the moment the session opens.

**Session-open failure is recoverable:** everything after `_startSession`'s health gate runs inside a try/catch. Any throw (e.g. `sendStart` on a duplex grpc-js has destroyed) routes through `_resetToIdle` — the one definition of "put this guild back where a wake word works again" — which ends the session, clears buffers/floor/gates and installs a fresh `VoiceSessionMachine`. `_tick` carries a matching recovery for any guild found non-idle with no open session, deliberately NOT gated on `g.session` (that is exactly what a failed open never sets); `g.sessionOpening` keeps it from tearing down a session that is merely slow to open — and because that flag *suppresses* the recovery, the one await in the open (`_contextBuilder`, i.e. Mongo/Qdrant/Mem0 via RecallService) carries a `CONTEXT_BUILD_TIMEOUT_MS` (15s) ceiling. A builder promise that never settles — a hung driver socket, not a rejection, which was always handled — would otherwise leave the guild `active` with no session and structurally disable the very recovery meant for that state. On expiry the open CONTINUES on the fallback context (configured system prompt, no recall, no history): a voice session that answers without memory beats one that never opens. The same reset handles a **clean sidecar-side stream close** (`session.on('end')`): the sidecar exits silently on two paths (no resumption handle, and a normal close classified `outcome = "closed"`), so `'end'` is often the ONLY signal the bot gets that its stream is dead.

**The `/voice` replies say what actually happened:** `join()` returns `{joined, reason, channelId}` and `listen()` returns `{listening, reason, channelId}`, and the command renders the refusals (already in a different channel, a session already active, no session opened because the sidecar was unhealthy) instead of reporting success for all of them. A `/voice listen` reply also names the `VOICE_MAX_SESSION_SECONDS` cap, because that cap — not `/voice leave` — is what usually ends listen mode (600s default, not overridden in the deployed overlay); when it fires, `_noteContinuousEnded` logs that continuous listen has ended and a wake word is required again. `leave()` attempts each teardown step (clear tick timer → `_endSession` → `connection.destroy()`) independently, deletes the guild entry unconditionally, and rethrows the first error for the command to report. Both halves matter: leaving the entry behind wedges the guild forever (`join()` short-circuits on it), but deleting the entry while SKIPPING `destroy()` is worse — the bot stays in the channel with a live `speaking.on('start')` handler, and the next `/voice join`, no longer short-circuited, wires a SECOND handler onto the same `AudioReceiveStream`, which is the duplicated-audio failure that made the wake word undetectable. A `listen()` that had to `join()` first also reports `joined: true` on failure, so the reply says the bot IS in the channel (wake word live) rather than reading as a total failure.

**`/voice listen` (admin override):** `VoiceSessionMachine.forceListen()` opens a session immediately with NO wake word and sets a `_continuous` flag so `turnComplete` stays "hot" with no teardown timer — continuous listening (no re-wake between questions) until `/voice leave` or the `VOICE_MAX_SESSION_SECONDS` cap. Gated to `BOT_ADMIN_USER_IDS` in `commands/slash/voice.js`. `listen()` grants the active-speaker floor (see below) to the invoking admin as part of opening the session — `forceListen()` alone never sets a holder, and without an explicit grant the floor-arbitration check in `_handleUserPcm`'s active branch withholds every speaker's audio unconditionally, so the session opens but nothing is ever forwarded to the model. As a result listen mode streams only the invoking admin's audio; any other speaker is withheld exactly as in a normal (wake-triggered) session. **With `VOICE_DEFERRAL_ENABLED=true` that stops being true after the first interjection:** the Phase 4 acknowledgment releases the floor, and the re-take path grants it to whoever speaks next — so a listen session silently becomes multi-speaker (one speaker at a time, floor passing between them) the first time someone qualifies as a waiter. Often desirable, but an admin running a controlled single-speaker demo should turn the deferral flag off for it, or expect the floor to move. Genuine per-speaker/simultaneous multi-speaker listen mode remains unimplemented.

**Web-search grounding:** the Live config sets `tools=[google_search]` (server-side grounding, no client tool-response plumbing) so the model answers factual/game questions from the live web. The voice-only system-prompt note (built in `VoiceService._appendVoicePersona` from the wake word) tells it to answer to the wake name and to USE search proactively rather than deflecting ("I don't play that game").

**Grounding is logged, not inferred (since 2026-09-29):** Live `server_content.grounding_metadata.web_search_queries` (google-genai 2.25) is collected per turn — distinct queries across every `server_content` message between turns, de-duplicated. The existing turn-complete INFO line carries it as the last item inside its parenthesised stats — `voice: turn complete (#K, audio_out=… chunks/…B so far, search_queries=N)` — and when N>0 one more INFO line `voice: web search (turn #K): <q1> | <q2> …` follows with every query in full (never truncated). A turn that never reaches `turn_complete` is still counted, by `_flush_turn_search`: on a barge-in (`web search (interrupted turn): …`), when a Live session closes under it — so on a drop + resume the dropped turn's queries neither bleed into nor dedupe against the resumed session's next turn (`… (unfinished turn, Live session closed): …`) — and in the session-END `finally` for `/voice leave`, the session cap or a control teardown mid-reply (`… (unfinished turn, session end): …`). Reading the logs: a `search_queries=0` turn-complete line immediately after a `web search (interrupted turn)` line is expected (Live can send `turn_complete` after `interrupted` for the same turn) — the search was logged and counted once under the interrupted label, not skipped. Each turn is flushed once. The `session END` line appends `search_turns=` (turns with ≥1 query) and `search_queries=` (total) after `sc_fallbacks` (then `hangar_edits=`, last — see "Member hangar"), and the `voice.session` span carries `voice.search_turns` / `voice.search_queries`. Before this, whether the model searched was only guessable from `[1, 2]` citation markers in the output transcript. Malformed/absent metadata is ignored (observability must never break the pump). See the SC section's "Disputed game mechanics" rule for why this was added.

**Neutral speaker marker (since 2026-10-09):** when an id-only SetSpeaker (a holder whose name didn't resolve) follows a NAMED `[SPEAKER: …]` marker actually emitted in the current Live session, the sidecar lazily sends `[SPEAKER: someone else]` before that speaker's next audio (`turn_complete=False`, counted in `speaker_markers`) so the model stops addressing them by the previous name; the persona note explains it means a different, unnamed person. Never on the empty-id clear, never in a session that started nameless, once per run of nameless speakers. `scripts/smoke-voice-identity.js` has an id-only segment C that asserts it's never read aloud.

**Hangar chat edits (since 2026-10-09):** with `HANGAR_EDITS_ENABLED` on (default when `HANGAR_API_URL` is set) the sidecar declares `hangar_fit` / `hangar_add_ship` / `hangar_reset` as local tools that edit the CURRENT SPEAKER's own hangar — the acting member is `SetSpeaker.user_id` (else the opener), never a tool argument. See "Member hangar" → "Chat edits" for the binding rule, fallback and logs.

**Reuses the `channel-voice` personality prompt:** `config.voice.systemPrompt` is wired from the same learned channel-voice system prompt used for text chat (falls back to `VOICE_SYSTEM_PROMPT` if set), so spoken replies match the group's learned communication style.

**Memory in, transcripts out:** recall context feeds into voice turns the same way it does text chat, and every voice exchange is written into the MongoDB message store as a transcript — it shows up in `/tldr` and centralized ranked recall like any other message.

**Speaker Identity & Name Resolution (Phase 3):** the bot knows who is speaking in voice channels and addresses people by their preferred names. **The member identity registry (`MemberIdentityService`, see "Member identity registry" below) is now the FIRST resolution layer** and the source of the `[SPEAKER: <name>]` marker's name; the order below follows it (an unset or failing registry falls straight through). **Voice also gets the who-said-what labels and roster** automatically: `VoiceService` already calls `buildTurnContext` at session open, so seeded history is labelled and the system prompt carries the roster (current speaker = session opener). **Known limitation:** a member who first speaks mid-session gets their address name via the marker but is not in the session-start roster (their aliases are not visible until the next session). The `[SPEAKER:]` name is also resolved once per join (`VoiceService._perUser`), so a `/whois` change mid-join, or a first utterance during the ~3s startup registry retry, keeps the earlier name until the next join. The `SpeakerNames` resolver (`services/SpeakerNames.js`) turns a Discord user into a name suitable for TTS (text-to-speech) by trying, in order: (0) the registry `addressName`; (1) an explicit override from `VOICE_SPEAKER_NAMES` config; (2) Discord's `globalName` (the account-wide displayable name); (3) per-guild `nickname` (server-specific override); (4) `username` with trailing digit runs stripped (`inc1067` → `inc`) to reduce redundancy; (5) `null` (omit the name marker). All candidates are **sanitised** (emoji removed, `™`/`(tm)`/bracketed-tag patterns stripped, zero-width chars removed, whitespace collapsed, capped at 24 chars) **because the names are read aloud** — an unsanitised nickname like `Macroplastics by Bic(tm)` would be voiced literally. The override is authoritative: it is only discarded if sanitisation yields empty (a letterless override like `007` is honoured). **A voice name that resolves to `null` is retried:** `_perUser` caches a name once it HAS one, but `lookupUser` (bot.js) is a cache-only Discord lookup, so a user the cache has not seen yet resolves to nothing on first contact. That miss used to be latched for the whole join — no `[SPEAKER: …]` marker and no deferral acknowledgment for that person until `/voice leave`. It now re-resolves at most once every `SPEAKER_NAME_RETRY_MS` (60s) per still-unresolved speaker; the per-frame path pays only a timestamp compare. **The VOICE path skips the nickname layer:** `VoiceService._perUser` calls `resolve(user, null)` — it has no per-guild `member` object to pass (voice sessions are keyed by Discord `userId`, not a guild-scoped message), so candidate (3) above never applies there. The chat/recall path (`bot.js`) does pass `message.member` and gets the full nickname layer. Practical effect: the same person can be resolved as their server nickname "Dave" in `/tldr`/chat but as their `globalName`-or-username fallback "dave42" in voice. The resolver feeds three systems: (1) **voice in-context markers** — on speaker change, the bot sends `[SPEAKER: <name>]` via the Live sidecar's `send_client_content` immediately before that speaker's next audio, context-only (not read aloud); (2) **chat and recall** — `/tldr`, channel context, and ranked recall use the same resolver so friends stop appearing as `inc1067` in text too (previously-stored rows keep their old names — no backfill); (3) **transcript attribution** — voice exchanges land in MongoDB with the floor-holder's real `userId`, not a placeholder. **Live model: `gemini-3.8-live`, `us-central1` only (since 2026-10-10).** The voice sidecar moved off `gemini-live-2.5-flash` after a smoke spike against three Live models on GEAP (`revenant-discord-bot-2`). **2.5-flash** read the out-of-band `[SPEAKER: …]` marker aloud in 2 of 3 identity runs, spoke ~150 citation brackets (`[1]`, `[1, 3]`) across the runs, never called `end_conversation` on "that's all", called each `sc_*` tool twice per question, and gave replies 2–4x longer. **`gemini-3.8-live`**: 0 marker leaks, 0 citation brackets, control 6/6 with the ordering the execution rule needs, one tool call per question, concise replies. `gemini-live-2.5-flash-native-audio` was rejected (control broken). **The old version lock is gone:** it existed because 3.x Live restricted mid-session `send_client_content` (the marker and the Phase 4 nudge depend on it) — 3.8-live allows it throughout the session — and because the 2026-09-26 re-check concluded 3.8-live 404s and lacks resumption/compression. That check probed `global` only: **3.8-live serves ONLY in `us-central1` on this project** (404 in `global`, `us-east4`, `europe-west4`) and there it supports session resumption, context-window compression and input/output transcription (Phase 2b is intact). So the voice sidecar sets **`GOOGLE_CLOUD_LOCATION=us-central1`** while the agent sidecar stays on `global` — changing `VOICE_LIVE_MODEL` means re-checking the location with it. Documented 3.8-live differences we do NOT configure around (Gemini API docs, `models/gemini-3.8-live` "Migrating" + `live-api/capabilities` "Model comparison"): `thinking_level`/`thinking_config` unsupported (we set none); proactive audio permanently on and affective dialog removed (we set neither); `send_client_content` with `turn_complete=true` unconditionally interrupts generation (only the Phase 4 nudge uses it, sent after playback drain); function calls default to async `NON_BLOCKING` with `WHEN_IDLE` response scheduling — control and `sc_*` declarations keep that default (the spike's control/SC results were measured under it), but the three `hangar_*` declarations pin `behavior=BLOCKING` so the model can't announce an edit before the write's result exists (write-then-read-back; `tests/test_live_bridge_hangar_blocking.py`). `voice-sidecar/src/config.py` carries the dated note and `tests/test_config.py` pins the default. Names are for directing a reply in a multi-person room; 3.8-live never volunteered one under the old "address people by name when it is natural" wording, and saying one every turn is noise, so the smoke now checks that the model KNOWS who is speaking (SPEAKER KNOWN) rather than that it says names. The same note also forbids speaking citation numbers / bracketed references aloud. **It must NOT say "never mention that you receive it"** (the pre-3.8 wording): 3.8-live follows that literally and, asked "what's my name?", answers "I don't have access to your personal information" (2/2 in a probe; 4/4 correct without the clause) — the deployed smoke's SPEAKER KNOWN failed 3/3 on it. Seeded history is unaffected: per-turn `send_client_content(turn_complete=False)` seeding was re-probed on 3.8-live and is used (3/3); `history_config.initial_history_in_client_content` is not needed.

**Human-like turn deferral (Phase 4 — "announce and release"):** when a second speaker talks while someone else holds the floor, their audio is withheld (as before) but no longer silently dropped — once the bot finishes speaking, it acknowledges the waiter by name in its own voice, then releases the floor so whoever speaks next takes it. **The trigger is playback drain (`_botIsSpeaking(g)` going false in `_tick`), never `turnComplete`** — `turnComplete` only means the Live model finished *generating*, and Gemini Live streams audio faster than real-time, so on a ~12s reply the model is done in ~2s while the bot is still talking for seconds after. Firing on `turnComplete` would cut the bot off mid-word. **The floor is released, not handed over:** handing it to someone the bot hasn't actually heard risks a deaf bot or a transcript filed under the wrong person, so `_tick` calls `g.floor.release()` and a companion re-take path in `_handleUserPcm` grants it to the next speaker — that re-take path is what makes "the next person to speak takes the floor" actually true; without it every speaker's audio, including the invited one's, would stay withheld until the follow-up window or session cap. **The re-take is level-triggered AND playback-guarded, and neither half is safe alone:** it fires on `vad.speaking` (not just the `justStarted` rising edge) because with `VOICE_VAD_MIN_SILENCE_FRAMES` ≈768ms an edge-only trigger strands anyone already mid-utterance — including a holder whose floor was released out from under them when server VAD endpointed them early (the same edge-vs-level bug as the 2026-08-14 outage documented in the holder branch). But a bare level trigger would let the bot's own acknowledgment, re-entering a laptop-speaker mic, seize the *unheld* floor and stream the bot's voice back as user input — so the re-take also requires `!_botIsSpeaking(g)`. It is additionally gated on `deferralEnabled`: the branch is provably dead with the flag off, so gating costs nothing and makes "flag off is byte-identical" structural rather than resting on an unpinned invariant a future `release()` site could quietly break. **Qualification requires a continuous overlapping utterance:** the per-user context tracks `withheldMs` (all withheld speech, cumulative) and a per-utterance `waitingMs` that is folded into `waitingPeakMs` on speech end, and the threshold is compared against `max(waitingPeakMs, waitingMs)` — the peak of any *single* utterance, plus whatever is in progress. A session-cumulative counter was wrong: three separate 300ms bursts would clear a 700ms bar no single burst ever reached, which is exactly the cough/backchannel/echo case the threshold exists to reject. (Do not "simplify" this by resetting on speech end — the acknowledgment is evaluated in `_tick` *after* the utterance ends, so a plain reset makes the value 0 at evaluation time and the feature never fires at all.) Only the overlap figure is thresholded, because the common case of someone talking into silence is not "trying to interject," it's just talking after the bot already finished. **`VOICE_ALLOW_BARGE_IN=true` is a hard prerequisite for any of this, not a nicety:** with barge-in off — which is the *code* default, though production sets it true — the half-duplex gate in `_handleUserPcm` returns before the non-holder accrual runs whenever the bot is producing audio, so overlap can never accrue, the acknowledgment can never fire, and the measurement log prints `0ms ... overlapping bot playback` on every single line, voiding the measurement-first rollout spec §5 makes a precondition. Non-overlapping withheld speech (`withheldMs`) still accrues, so the log looks alive while the number that matters is structurally pinned at zero. **`VOICE_DEFERRAL_MIN_SPEECH_MS` (default 700) is a placeholder, not a trusted value** — the withheld-speech debug log (`VoiceService.js` near the non-holder branch) prints all three figures (total withheld, this utterance's overlap, longest single overlapping utterance **of the current turn**) specifically so the real threshold can be set from the **longest-single-utterance** number in logged data — not the cumulative one, which will read far higher (headphones vs. laptop-speaker echo re-entering a mic is the failure mode this measurement is guarding against) before the flag is flipped on. **Critical when reading those numbers: ~768ms of the figure is VAD hangover, not speech.** `SileroVad` latches `speaking: true` until `VOICE_VAD_MIN_SILENCE_FRAMES` (24 × 32ms) of sub-threshold audio has passed, and the accrual counts every chunk while that latch is open — so as long as packets keep arriving (Discord's `AfterSilence` is 800ms, so they usually do) a **64ms** utterance accrues **~760ms**, and a 320ms one accrues ~1020ms. Measured, not theorised. Consequence: at the 700 default the threshold rejects *nothing* — any utterance the VAD detects at all clears it, which quietly voids spec §5's "coughs, one-word backchannels, and echo bursts do not earn an announcement" and §10's top-listed mitigation. Treat ~768ms as the **noise floor** of the logged figure; a bar that means anything wants to sit materially above it (~1300–1500ms ≈ 500–700ms of genuinely voiced speech). The logged numbers are self-consistent with the production check (same code path), so a threshold read off logs is not *wrong* — it is just measuring latch-open time, not speech. The alternative is a code change to discount the hangover (accrue only while the silence run is zero, or subtract `minSilenceFrames × 32ms` when folding the peak) — a parked follow-up. The `[SYSTEM: …]` nudge is injected by the sidecar with `turn_complete=True` (unlike the Phase 3 `[SPEAKER: …]` marker's `turn_complete=False`) because a reply is actually wanted here; its phrasing is delegated to the learned channel-voice persona rather than scripted, so the acknowledgment stays in character — the persona clause that explains `[SYSTEM:` lines is itself gated on `VOICE_DEFERRAL_ENABLED` so the prompt never describes a mechanism that can't fire. **Qualification is scoped to the turn it was earned against:** opening a new turn clears every speaker's `waitingMs`/`waitingPeakMs` (not `withheldMs`, which is the session-scoped measurement total), because a turn can end without its drain-time acknowledgment ever firing — the holder makes any sound before playback drains, the machine goes `hot`→`active`, and the check is skipped. Without the turn-boundary clear, a waiter who qualified against turn N and has been silent (or has left) ever since is named at the drain of turn N+1, apologising for talking over a reply two turns old. Spec §9's rejection of TTLs was about the waiting *queue*, not a missed drain. The `FloorControl` waiting set itself is untouched: a stale waiter stays listed but can no longer clear the threshold. **The floor is only released if the nudge actually went out:** `VoiceClient.sendAcknowledgeWaiting` returns a boolean and `_tick` latches/releases/clears only on `true`, retrying with exponential backoff (1s→30s) otherwise. That boolean is *not* a delivery receipt — grpc-js reports a write to a half-dead duplex as an async `'error'` event rather than a synchronous throw, so a nudge can still be lost with the send reporting success; a sidecar→bot confirmation for `AcknowledgeWaiting` is the real fix and is a parked follow-up. An empty `SetSpeaker` (`{userId: '', displayName: ''}`) now **clears** `current_speaker`/`pending_speaker` on the sidecar instead of being ignored — this closes a hazard Phase 3 flagged but couldn't reach (with exactly one floor holder per session, the speaker never legitimately went to "unknown"; a released-then-retaken floor breaks that invariant). Tunables: `VOICE_DEFERRAL_ENABLED` (default **false**, the kill switch — off is byte-identical to pre-Phase-4 behaviour with exactly one asterisk: the withheld-speech *debug log*'s "longest single utterance" figure is now per-turn rather than per-session, deliberately, because the measurement has to measure the quantity production thresholds on. No send, floor, or prompt change with the flag off) and `VOICE_DEFERRAL_MIN_SPEECH_MS` (default 700 — **almost certainly too low; see the ~768ms noise floor above before tuning it**). Spec: `docs/superpowers/specs/2026-08-14-voice-phase4-deferral-design.md`.

**Member identity registry:** Mongo collection `member_identities` (`{_id: discordId, addressName, aliases[], updatedBy, updatedAt}`), owned by `services/MemberIdentityService.js` (`bot.memberIdentity`, constructed in `bot.js` before `SpeakerNames`). **Cache:** loaded fully into memory (reads are sync and never touch Mongo); startup load retries every 3s until Mongo answers, then refreshes every 60s; writes are serialised behind a write lock and reload the cache themselves, and a stale-load guard stops an older in-flight load from clobbering a newer write. Writes return `unavailable` when Mongo is down (do not gate writes on `isLoaded()`). **Validation (`services/identity/validation.js`):** names are sanitised like `SpeakerNames` (emoji/tags/zero-width removed, separator characters stripped so a name cannot forge a `[Name · id]` label, 24-char cap), must contain a letter, be 2+ chars (longer names are shortened to 24), and contain no run of 15 or more digits (rejects pasted Discord IDs, another label-spoofing vector); max 10 aliases per member. **Collision rule:** a name held by ANOTHER member's addressName or alias (case-insensitive) is rejected with `taken` and the holder's ID; an alias equal to the member's own address name is a no-op. **`/whois`** (`commands/slash/WhoisCommand.js`): `show [member]`, `address <name> [member]`, `alias-add <alias> [member]`, `alias-remove <alias> [member]`; all replies ephemeral; anyone edits themselves, editing another member requires `BOT_ADMIN_USER_IDS` (`isAdmin`), `show` is open to everyone; `show` for a member with no record says so and prints the name the bot currently resolves for them. **Seed script:** `node scripts/seed-member-identities.js` (dry run) / `--apply` inserts `addressName` from `VOICE_SPEAKER_NAMES` for IDs with no doc and never overwrites (seed docs carry `updatedBy: 'seed'`); run it from the bot pod (needs the Mongo URI).

**`VOICE_SPEAKER_NAMES` (bot env):** optional JSON `{"<userId>":"<spoken name>", …}` providing name overrides. Example: `{"123456789":"Mike","987654321":"Alex"}`. Malformed JSON is tolerated (falls back to `{}`). **Requires a pod restart to reload.** Stored in the deployed configmap. Names are sanitised the same way as resolver candidates (emoji/tags removed, 24-char cap, etc.), so an override like `😂 LOL 😂` is sanitised to `"lol"` and then matched/honoured if non-empty.

The sidecar emits markers via `send_client_content(..., turn_complete=False)` immediately **before that speaker's next audio** so the marker is context only and not read aloud. **It also re-announces the current named speaker's marker before the first audio of EVERY new turn** (after each `turn_complete`, via `_SessionRef.turn_ended`; logged `voice: speaker re-announced for new turn: <name>`, counted in `speaker_markers`) — not only on a speaker change. Why: on gemini-3.8-live a marker one exchange old was lost — Sarah's "what's my name?" after her own earlier turn got "your name hasn't been mentioned to me yet" in 1–2 of 6 real-model smoke runs even with the prompt fix. Never re-announced after the empty-id clear or for an unnamed speaker (the neutral marker is not repeated). The prompt tells the model these `[SPEAKER: …]` lines are out-of-band metadata **never to read aloud**, and to address people by name when natural (e.g. "Hey Mike, …" or "Great question, Alex"). Markers are counted as `speaker_markers` in the session END log.

**Voice control commands (end / go quiet):** two spoken commands work from inside a live voice session — "thanks jarvis, that's all" (or "end conversation") ends the current session — once the bot's short spoken confirmation has played (see the execution rule below; this is NOT immediate) — instead of waiting for the follow-up/idle timeout, and "go quiet for ten minutes" (or "stop listening for 20 minutes") does the same AND ignores the wake word from everyone in that guild's channel until the deadline. **Detection is two layers, either is sufficient:** the voice sidecar declares two local Live function tools, `end_conversation()`/`go_quiet(minutes)`, answered immediately with `{"ok": true}` so the model can speak a short confirmation and emits a `Control` server event (`proto/voice.proto` `VoiceServerEvent.control`, field 7, `action` `"end"`|`"quiet"`); independently, the bot matches the turn's accumulated input transcript against `services/voice/controlPhrases.js`'s pattern set (`matchControlPhrase`) — model cooperation is not required for the phrase path to fire. **The phrase check runs ONCE per input turn, on the complete utterance**, at the first sign the model is replying (first output audio or output transcript) or at `turnComplete`, whichever comes first — never per transcript fragment (a prefix like "stop listening" would fire before " to him" lands). An empty input buffer at that point does not use the check up, so input transcription that lands after the first reply audio is still checked at `turnComplete`. A barge-in (`interrupted`) re-arms the check and starts the match window at the current end of the input buffer. **Known limitation:** if SOME input fragments arrive before the first reply audio and the rest after it, the check runs on the partial utterance and is spent, so the phrase backstop can miss — the model-tool path covers that case. **Phrases are anchored at the START of the utterance:** only a short lead-in may precede the command (wake phrase/bot name — hey/hi/ok/okay + jarvis/revenant or another built-in wake name — "please", "thanks"/"thank you", "can/could/would/will you", "alright", "ok so"; `LEAD_IN_UNITS`), so ordinary speech that merely contains a verb ("how do I mute", "tell him to shut up", "should I go quiet", "don't end the conversation yet") never fires, and a negation before the end verb is rejected structurally. Quiet verbs accept only a duration/politeness tail ("mute alex" rejects); "end the conversation" only an address/sign-off tail; "that's all"/"we're done" must be a closing STATEMENT — lead-in, phrase, address tail, end of utterance — so "let me know when we're done", "until we're done", "is that all", and the question "and that's all?" never fire. **Enforcement is bot-side and idempotent** (`VoiceService._requestControl`): the tool path and the phrase path firing for the same utterance is harmless — the first request wins, and a `quiet` request upgrades an already-pending `end` (so "end conversation, actually go quiet for ten minutes" in one breath ends up quiet, not just ended). **Execution rule (`_tick`):** a pending command executes when ALL of (1) the model's reply turn has produced output for it (audio or an output transcript seen after the request — `pendingControl.outputSeen`), (2) a `turnComplete` arrived after the request and after that output (`replyCompleted`), and (3) playback has drained (`_botIsSpeaking(g)` false) — OR, failing that, when `CONTROL_DRAIN_CEILING_MS` (10s) has passed since the FIRST request (duplicates never extend it), in which case teardown proceeds even with playback still running and can cut the confirmation off. Condition (1) is load-bearing: Gemini Live emits a bare `turnComplete` for the TOOL-CALL turn itself (`audio_out=0`) ~10ms after the tool call, the spoken confirmation only starting ~250ms later, and the sidecar's `Control` reaches the bot before that bare `turnComplete` — counting it tore the session down before the confirmation existed. A phrase request created AT a `turnComplete` waits for the next reply; one created at the first reply audio counts that audio. A reply that never produces output falls to the ceiling. The sidecar emits `Control` BEFORE awaiting `send_tool_response` (so a hung send can't delay or lose the command); that is safe precisely because of this rule. While a command is pending, the Phase 4 waiter acknowledgment is skipped (the session is about to end). **Quiet mode gates the idle-state wake branch entirely** — while `now < g.quietUntil` the bot skips wake-word detection AND stops accumulating the per-speaker pre-roll buffer for that guild (no audio is retained or forwarded to the model while quiet); expiry is noticed (and logged at INFO) both on the next audio frame and in `_tick`, so the log line lands promptly even with no one talking. Duration is **clamped 1–120 minutes, defaulting to 15** when unparseable/omitted (`QUIET_MIN_SECONDS`/`QUIET_MAX_SECONDS`/`QUIET_DEFAULT_SECONDS`). **`/voice resume`** (anyone in the guild, not admin-gated) ends quiet early and reports how much time was left; it also cancels a still-pending "go quiet" whose confirmation hadn't finished playing yet (`resume()`'s `cancelledPending: true`), which the command reports distinctly ("Cancelled the quiet request…") rather than claiming quiet had already started. `/voice leave` and a fresh `/voice listen` both clear quiet as part of resetting guild state. **Kill switches:** bot `VOICE_CONTROL_COMMANDS_ENABLED` (default **true** — off disables the phrase backstop and makes the bot ignore `Control` events) and sidecar `VOICE_CONTROL_TOOLS_ENABLED` (default **true** — off stops the two tools from being declared to Live at all, independent of the Star Citizen knowledge tools). **Real-model smoke:** `scripts/smoke-voice-control.js` (see its header for the port-forward command) streams three fixtures — "go quiet for two minutes" (asserts a `quiet` control event, seconds 120), "that's all, thanks jarvis" (asserts an `end` control event), and a **negative** fixture "that's all I know about shields, what do you think?" (asserts **no** control event, guarding against the model firing `end_conversation` on a mid-sentence phrase lookalike) — and for the two positive fixtures it also FAILs unless model audio arrives AFTER the control event and BEFORE the final `turn_complete` (the ordering the execution rule depends on; the timeline, including bare `turn_complete`s with `audio_out=0`, is printed). It exercises the model-tool path only; the phrase backstop is unit-tested directly.

**Deploy checklist:** (1) run the Task 1 GEAP pre-flight probe and set the confirmed model as `VOICE_LIVE_MODEL` in the deployed overlay (never the `REPLACE_WITH_VALIDATED_MODEL` placeholder from the tracked manifest); (2) confirm the bot image is rebuilt from the Debian/glibc (`node:24-trixie-slim`) `Dockerfile` before flipping `VOICE_ENABLED=true` — the vendored openWakeWord ONNX models are baked into the image (no key/secret or PVC needed); (3) apply from the **deployed overlay**, never the tracked manifests — `kubectl apply -f k8s/overlays/deployed/voice-deployment.yaml -f k8s/overlays/deployed/voice-service.yaml -f k8s/overlays/deployed/voice-networkpolicy.yaml -n discord-article-bot` (or, for an image-only change, `kubectl set image deployment/discord-article-bot-voice voice=mvilliger/discord-article-bot-voice:<sha> -n discord-article-bot`) — then redeploy the bot and run `scripts/registerCommands.js`. **Do NOT run `kubectl apply -f k8s/voice/`:** the tracked `voice-deployment.yaml` is pinned to the literal placeholder `REPLACE_WITH_SHA`, which does not exist on Docker Hub, so applying it rewrites the live image to a broken tag and the rollout stalls in `ImagePullBackOff` (RollingUpdate keeps the old pod alive, so it presents as a 120s timeout rather than an instant outage — but the deployment is now pinned to a tag that will fail on the next reschedule). The same apply also reverts the deployed Service and NetworkPolicy to their tracked placeholder forms. This is the same `k8s/overlays/deployed/` source-of-truth rule stated above, which the voice checklist previously contradicted; (4) if the session-longevity work (compression + resumption) is meant to be observable, raise `VOICE_MAX_SESSION_SECONDS` above its 600s default first — otherwise `VoiceService._tick`'s hard cap ends the session before the ~15-min Live limit it's meant to work around is ever reached; (5) **before gathering any Phase 4 deferral measurements or flipping `VOICE_DEFERRAL_ENABLED=true`, confirm `VOICE_ALLOW_BARGE_IN=true` is set in the deployed configmap.** It is a prerequisite, not a nicety: the half-duplex gate returns before the overlap accrual, so with barge-in off the qualifying figure is pinned at zero, the acknowledgment can never fire, and every measurement line reads `0ms ... overlapping bot playback`. Production sets it true today, but nothing enforces it.

**Deferred follow-ups (not yet implemented):** idle auto-leave (channel currently requires `/voice leave`), dynamic (session-time, non-static) voice-profile injection into the Live system prompt, playback jitter smoothing (occasional; likely a jitter buffer + proper 24k→48k resampler), and self-service speaker names via `/voice name @user <spoken name>` command (Phase 4 — move the override table from the configmap to MongoDB so users set their own preferred spoken names; the configmap seed layer remains as the default).

**Manifests:** `k8s/voice/` (tracked) — see its README for the apply order, the required bot ConfigMap/Secret/NetworkPolicy edits, and the build/push command.

**Layer-4 real-model smoke test (speaker identity):** `scripts/smoke-voice-identity.js` opens ONE real `Converse` gRPC session against a port-forwarded sidecar and drives a scripted two-speaker conversation using two distinct synthesized voices (`scripts/gen-test-voices.js` TTS fixtures, auto-generated into gitignored `voice-fixtures/` if missing), so the three things that are only observable against the real model get checked without Discord or a second human: the model never reads the `[SPEAKER: ...]` marker aloud (critical — non-zero exit if it does), it never speaks a bracketed citation like `[1]`/`[1, 3]` (CITATION SILENT, critical — speaker A's weather question triggers search), it knows who is talking (**SPEAKER KNOWN**, critical, since 2026-10-10: right after Sarah has spoken following Mike, Sarah — still the floor holder, so no new SetSpeaker, like the bot — asks "what's my name?" from `voice-fixtures/whats-my-name.wav`, same TTS voice as her first clip; the reply must contain "Sarah" and not "Mike"), one question doesn't produce more than one full reply, and each input transcript is printed next to the speaker that was current when it arrived for a human eyeball on attribution. SPEAKER KNOWN replaced NAMES USED, which rewarded saying a name on any reply — contrary to the names rule above. An informational **NAME RATE** line prints `N/M replies used the speaker's name` for Mike's and Sarah's first replies and flags `(overuse?)` above 2/3. Pure verdict helpers live in `scripts/lib/voiceSmokeChecks.js` (unit-tested); a missing what's-my-name clip is generated with `node scripts/gen-test-voices.js --missing` (only clips not on disk). Run with `kubectl port-forward svc/discord-article-bot-voice 50051:50051 -n discord-article-bot &` then `node scripts/smoke-voice-identity.js`. Against a sidecar build that predates `SetSpeaker` the marker is silently dropped server-side, so SPEAKER KNOWN legitimately FAILs there — the script says so rather than crashing.

**Layer-4 real-model smoke test (Star Citizen knowledge):** `scripts/smoke-voice-sc.js` follows the same pattern (one real `Converse` session per question, single-speaker TTS fixtures) to check the one thing unit tests can't reach — whether the live Gemini Live session, with sc-knowledge's tool declarations attached, actually answers Star Citizen questions correctly. It asks the four canonical questions from `agent-sidecar/eval/sc_eval_set.py` plus a fifth Scorpius ship-purchase question and a sixth tool-less mechanics question ("why do I have to spool my quantum drive in NAV mode…", from the 2026-09-29 dispute — expect a `voice: web search (turn #K): …` line / `search_queries>0` for it rather than a `tool_call`), waits up to 45s per question for `output_transcript` text, and checks each transcript (case-insensitive) for an expected fact. **CITATION SILENT** (critical, since 2026-10-10) fails the run if any answer's output transcript contains a spoken bracketed citation (`[1]`, `[1, 3]` — `gemini-live-2.5-flash` read ~150 of these aloud in the model spike); offending transcripts are printed in full and listed in the SUMMARY. ## Slash Command Development Guidelines

When creating or modifying slash commands:

1. **Service method signatures**: Verify correct method names and parameter order by checking the service implementation
   - Example: `resetConversation(channelId, personalityId)` - channelId comes first
   - Example: `listUserConversations(userId, guildId)` - requires guildId parameter

2. **Service enabled checks**: Optional services (Mem0, Qdrant, etc.) need `isEnabled()` checks at the start of execute()
   ```javascript
   if (!this.mem0Service.isEnabled()) {
     await this.sendReply(interaction, {
       content: 'Memory feature is not enabled on this bot.',
       ephemeral: true
     });
     return;
   }
   ```

3. **Error handling patterns**: Some errors should not have "Error:" prefix
   - Conversation limit reasons ('expired', 'message_limit', 'token_limit') are informational, not errors

4. **Default values**: All chat commands should default to `friendly` personality when none specified

5. **Formatter usage**: Use service formatters (e.g., `qdrantService.formatResult()`) for consistent output

## Debugging Common Issues

### Duplicate Messages / Multiple Replies

**ALWAYS CHECK FIRST**: Are there multiple bot instances running with the same Discord token?

```bash
# Check ALL namespaces for bot deployments
kubectl get pods -A | grep -i discord
kubectl get deployments -A | grep -i discord
```

Multiple instances with the same token will ALL receive Discord events and ALL respond, causing:
- Duplicate replies (different content if conversation contexts differ)
- One reply faster than the other
- Replies with stale/old conversation context

**Root cause example (Dec 2025)**: A forgotten deployment in `default` namespace ran alongside the production deployment in `discord-article-bot` namespace for 10 days, causing duplicate replies to every message.

### Local LLM Fallback Behavior

When the local Ollama instance becomes unavailable mid-runtime, the bot automatically falls back to the cloud provider:

- **Circuit breaker**: After a connection error (ECONNREFUSED, ETIMEDOUT, etc.), `LocalLlmService` is marked temporarily unavailable for 60 seconds
- **Fallback personality**: The `uncensored` personality defines `fallbackPersonality: 'friendly'` — when local LLM fails, the request is retried with the `friendly` personality via OpenAI
- **User notification**: A visual notice (warning emoji) is shown to the user when fallback occurs
- **Recovery**: After the 60-second cooldown, the next request optimistically tries the local LLM again
- **Custom fallbacks**: Any `useLocalLlm: true` personality can define its own `fallbackPersonality` field
