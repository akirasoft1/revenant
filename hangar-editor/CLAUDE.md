## Terminal view

**Terminal view (since 2026-10-11).** Spec: `docs/superpowers/specs/2026-10-11-hangar-terminal-view-design.md`. A second ship-detail layout modelled on the in-game ship terminal, beside the original table now called **Classic**. **Toggle** shows at viewport ≥ 900px only (below that Classic is the only layout — no mobile Terminal yet), the choice persists in `localStorage` key `hangar.shipView`. Keyboard: `A`/`D` previous/next slot, `R` reset the selected slot, `Esc` switches back to the Classic view (`onExit`). **`TerminalBoundary` falls back to Classic** if the lazily-loaded Terminal chunk fails to load (stale deploy, flaky network), so a broken chunk never blanks the ship page. **Images are hotlinked, not proxied/stored:** hosts `cdn.star-citizen.wiki` and `media.starcitizen.tools` (a site-wide footer reads "Unofficial fan site — not affiliated with Cloud Imperium Games. Images: Star Citizen Wiki / starcitizen.tools."). **Image hosts have ONE source of truth, `IMAGE_HOSTS` in `hangar-service/src/catalog.py`:** the CSP `img-src` is built from it AND `_first_image` only returns URLs on those hosts (https only, preferring the wiki CDNs, then `cstone.space`), so an image on any other host is dropped server-side and the editor shows the type icon instead of a CSP violation. `cstone.space` was added 2026-10-11 after a CSP-blocked report — the Wiki lists it FIRST for ~13% of component items (62/474); to support a new host, add it to `IMAGE_HOSTS`. An `<img>` that fails reports to hangar-service, which logs the WARNING `hangar: image load failed host=… url=… context=… member=…` (no truncation) — the report endpoint is `POST /api/v1/client-events/image-error`, browser-session only (service tokens get 403), same-origin checked, rate-limited to 20/min per member (429); that line is the only signal that a hotlinked URL has rotted. **Catalog additions (all optional, so older clients/cached data still parse):** slot options carry `image`, `manufacturer`, `description`, `stats`; vehicles carry `image` (the ship-panel hero: a media.starcitizen.tools thumbnail rewritten to 1280px — `HERO_WIDTH` in catalog.py; the 600px default is soft at panel size and the 3840px originals are ~1 MB — else the `original_url`, else `thumbnail_url`; item images stay thumbnail-first), `dimension`, `mass`, `crew`, `portCounts`. **Positions:** Firestore doc `vehiclePositions/{vehicleUuid}` and the read route `GET /api/v1/catalog/vehicles/{uuid}/positions` (404 for an unknown vehicle, `{}` when no doc exists). The only writer is the admin wireframe upload (see `hangar-service/CLAUDE.md` "Ship wireframes — server side"), which stores 3D `xyz` hardpoint positions (`source: "extracted"`); the Classic and render panels still draw only the older 2D `view`/`x`/`y` points, of which none exist. The earlier plan to hand-place 2D points and import extracted positions separately was superseded by the wireframe pipeline. **Next (follow-ups, in order):**

1. **Weapon/item wireframes** (`kind: "item"`) in the cards and compare panel — format, storage and viewer are already keyed by `kind` + class name; the server only accepts `vehicle` today.
2. **Per-ship camera presets** / saved default orientation.
3. **Deployable parts** — landing gear up, wings in flight pose; needs animation data from the export (wireframes show the parked pose, gear down).
4. **Mobile Terminal layout.**
5. **Loose inventory** — items members own but haven't fitted (the in-game grid shows owned items; ours shows compatible catalog items).
6. **FX conversion** for mixed-currency pledge leaderboards (totals are per currency today, USD ranked first).
7. **Our own HTF extension/bookmarklet** producing Hangar Transfer Format directly — only if HangarXPLOR breaks.

## Ship wireframes — viewer

**Ship wireframes (since 2026-10-11).** Spec: `docs/superpowers/specs/2026-10-11-ship-wireframes-design.md`. The Terminal view's ship panel (`ShipPanel.tsx`) shows a rotatable wireframe of the ship with markers at the REAL hardpoint positions (the end-state look the old placement-tool plan was reaching for). When `vehicle.hasWireframe` it is the **default**, with a `Wireframe | Render` switch remembered per browser in `localStorage` `hangar.shipVisual` (try/catch, anything unreadable → wireframe); ships without one show the render panel unchanged. **Level of detail + Expand (same day, after the owner reported a fuzzy Ironclad):** bundles are ordered longest line first, and the viewer draws only a prefix — lines ≥ `MIN_LINE_PX` (2) CSS px on screen, at most `MAX_LINES_PER_PX` (40) per pixel of the ship's on-screen size, never fewer than `MIN_LOD_LINES` (1,500) (`lodLineCount`, `hangar-editor/src/lib/wireframe.ts`; applied in `stage.ts` before every draw). 60,000 additive lines in a 250 px panel is ~240 lines/px and reads as a glow; the cap was set from the full-window views the owner approved (30–45/px). So the pipeline's longest-first order is now load-bearing for the viewer (an unordered bundle is simply never thinned). In wireframe mode the ship column is the widest (`.t-body:has(.t-shippanel.has-wire)`), the panel is `clamp(340px, 46vh, 560px)`, and an **Expand** button makes it cover the whole terminal body; while expanded, Esc collapses it (capture-phase `preventDefault`, which the ActionBar's Esc-to-Classic handler respects). **Hidden-line removal (same day, the fix that actually worked):** thinning lines did NOT fix the fuzzy look — a see-through wireframe of a dense ship is a glow at any line count. Bundles built by tool ≥ 1.1.0 carry an optional header `views` (the 26 depth-map directions, unit vectors toward the viewer) plus `uint32 LE × lines` after the line data (bit i = visible from `views[i]`; payload is then `lines × 16`, validated by `swf.py` and `lib/swf.ts`). The per-view test (`DepthMaps.point_mask`) is deliberately more forgiving than the keep/cull test: front within `MASK_EPS_PX` (3) pixels of the sample in the point's OWN depth pixel, as long as that sample is within `MASK_STEEP_PX` (6) of the closed map — otherwise steeply viewed surfaces hide themselves, and without the second condition a sampling pinhole lets buried lines through. The viewer (`blendViews` / `writeLineAlpha` in `lib/wireframe.ts`) fades each line by the baked views within 18–38° of the camera direction, keeps unseen lines as a faint ghost, recomputes only when the camera direction moves, and supersamples the canvas (2× device pixel ratio, cap 3) for finer lines; the per-pixel density cap is off for such bundles. Old bundles still load and draw the old way — **rebuild and re-upload after a pipeline change that affects the bundle.** **How to look at the viewer without a GPU or a browser session:** bundle a tiny entry that imports `stage.ts` with esbuild and screenshot it with Playwright's `chrome-headless-shell` (`--use-angle=swiftshader --enable-unsafe-swiftshader --timeout=7000 --screenshot`, NOT `--virtual-time-budget`, which hangs on the gunzip stream) — tuning this blind twice produced nothing; one screenshot found the real problem.

- **Editor:** `three` lives ONLY in the lazily loaded `WireframeViewer-*.js` chunk (`React.lazy`, ~560 kB / ~140 kB gzip, fetched the first time a wireframe shows); pure helpers are in `lib/wireframe.ts` and `lib/swf.ts` (decode: gunzip, parse header, dequantise). Additive cyan `LineSegments` (opacity 0.32), orbit controls with damping, auto-rotate until first interaction, green markers (selected: white, larger, pulsing) at each loadout slot with an `xyz`, hover label, click selects, selecting a port pans toward it; `prefers-reduced-motion` turns off auto-rotate, pulse and easing. **Render on demand** (`needsFrame`): a still wireframe draws nothing — frames only while something changed or auto-rotate/easing/pulse runs, never off-screen or in a hidden tab. In wireframe mode the **panel is taller and the ship stats move to a compact strip under it** so nothing covers the model. The bundle is fetched with TanStack Query (`['wireframe', uuid]`, fresh for a day, a 404 for 30 s; ETag revalidation); **in-session refresh:** a changed `positions` object or `hasWireframe` for the open ship invalidates the query, so a model uploaded/replaced/deleted while the page is open appears without a reload. **Fallbacks never block the panel:** no WebGL or no `DecompressionStream`, a bundle that 404s or fails to fetch/decode, a lost GL context, or a viewer chunk that fails to load (stale deploy) → the render panel with a short note in place of the switch.
- **Admin page `/admin/models`** (`AdminModelsPage.tsx`; nav link hidden and the not-found page shown for non-admins): multi-file picker/drop zone for `.swf.gz` (other files rejected in the browser), uploads up to `UPLOAD_CONCURRENCY = 3` in flight, **paced: at least `UPLOAD_MIN_INTERVAL_MS = 2000` between upload STARTS (~30/min)** because each upload makes the server do a Wiki detail fetch for an uncached vehicle and that limiter (60/min) is shared with every hangar read, so an unpaced 220-ship batch would make the bot's hangar tools answer `unavailable` for minutes (a full set takes about 8 minutes; the page shows a pacing note and an ETA; Retry failed is paced too), with a running `N / M uploaded, K failed` line and per-file results (ship matched, slots matched/missing/ambiguous), **Retry failed**, a sortable/filterable table of stored models, **Preview** (the same viewer in a dialog, only for models with a ship) and **Delete** (confirm). After a drained upload batch or a delete it invalidates the `models`, `vehicle-slots`, `vehicle-positions` and `wireframe` query caches so an open ship page updates.

Server-side storage, upload validation, slot matching, routes and known limits: `hangar-service/CLAUDE.md` "Ship wireframes — server side".

## Slots from fitted items

Spec: `docs/superpowers/specs/2026-10-11-hangar-item-slots-design.md`. The server rules are in `hangar-service/CLAUDE.md` "Slots from fitted items".

- **Editor:** dynamic slots render like any nested slot (both views group by type and label `parent › child`); after a fit/reset the hangar is re-read and that ship's slot-options cache dropped; dropped fittings are named in a notice (`lib/dropped.ts`); a Terminal selection whose slot disappeared moves to its nearest surviving ancestor; a slot with no wireframe position of its own uses its nearest ancestor's (the turret's node).
